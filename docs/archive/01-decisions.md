# SoloChat 设计决定记录

本文件记录**为什么**这样做，而不是做什么。当前做到什么见 [HANDOFF](../HANDOFF.md)，后续目标见 [11](11-next-goals.md)；[00](00-plan.md) 保留原实施方案。
每条决定都写清：决定了什么 / 为什么 / 放弃了什么替代方案 / 什么情况下应该推翻它。

---

## D1. 形态：Android 原生 App，不是网页，也不是桌面端

**决定**：只做 Android 原生（Kotlin + Jetpack Compose）。局域网网页版作为后续阶段，架构上预留。

**为什么**：用户明确"只在 Android 上使用"。原生能拿到通知、前台服务、分享、输入法这些聊天软件的基本盘；网页做不到可靠的后台与通知。

**放弃的替代方案**：
- Flutter：一套代码能出 iOS，但用户没有 iOS 需求，且与 Android 原生能力（前台服务类型、通知渠道）之间多一层摩擦。
- 纯 PWA：最快能用，但没有原生通知、后台受限，"像在用微信"这个核心体验立不住。

**什么时候推翻**：如果后来要做 iOS，`core/` 是纯 Kotlin（不含 Android API），可以搬进 Compose Multiplatform 共用；UI 层需要重写。

---

## D2. "服务端常驻" = App 内的前台服务，不是外部服务器

**决定**：所有逻辑跑在手机 App 内，由前台服务（`AgentForegroundService`）保证常驻。不做外部 Node 服务。

**为什么**：
- 用户要的是"只在 Android 上用"，那"服务端"就是 App 自己。
- 数据只有一份、离线可用、Key 不离开手机。
- 用户的"服务端常驻"需求，实质是**主动消息要可靠**，而前台服务 + 常驻通知已经能解决（RikkaHub 用的就是这个做法），不需要外部机器。

**放弃的替代方案**：PC 上的 Node 服务 + 手机当客户端。优点是算力/电量/USB 拔了也不怕；缺点是引入一台常开机器、数据离开手机、多一跳网络依赖。**如果以后要"手机电脑同一份数据"，再考虑。**

**代价与约束**：必须在阶段 1 就规划好 Android 14+ 的前台服务类型声明、通知权限、电池优化引导。这些**不能事后补**（改 Manifest 的 service type 会牵动发布与权限）。

---

## D3. 一轮 = 一次 API 调用，输出"事件脚本"而不是多次工具调用

**决定**：模型每轮只被调用一次，返回一段带时序的事件脚本（`say/act/scene/wait/read`）；引擎负责按节奏播出。

**为什么**：这是成本与语义双重最优。

- **成本**：工具驱动方案下，一轮 3 条消息 = 3 次决策 = 完整前缀重发 3 遍（缓存命中约 1/10 价，但不是免费，且前缀随历史增长越来越大）。脚本驱动下输入量 = 普通聊天的 1 倍。
- **语义**：工具驱动会让模型把"一次连贯的说话"拆成多次决策，从而写元文本（"已经发了问号，接下来补一句"）、重复、把连着的两句话拆断。脚本驱动让模型只思考一次"我该怎么回"。

**放弃的替代方案**：工具驱动的 `send_message`（QQ-agent 的做法）。它在群聊场景是合理的（多一次往返只是慢一点），在一对一私聊里代价太大——用户体验全挂在"这条什么时候出现"上。

**什么时候推翻**：如果发现模型无法稳定输出结构化脚本（某些小模型），可以退回"半结构化"——只要求 `gap_ms` 可选、正文是纯文本，解析器降级成单条 `say`。协议保留了这个降级路径。

---

## D4. 生成与播出彻底解耦

**决定**：模型生成完一轮内容后，请求立即结束；播出由播放器异步执行。

**为什么**：这是"中途改口"能做到零 API 成本的前提。用户在播出中途插话时：
- 取消未播事件（`canceled`）
- 正在播的事件标 `interrupted`
- 已播的就是说过了，不回滚

如果生成即发送，打断就只能再调一次模型去问"我改口"，成本翻倍。

**代价**：播放器的状态机（`pending/playing/delivered/canceled/interrupted`）是整个项目最容易被写错的地方，**必须有完整的中断矩阵测试**。

---

## D5. 事件类型只留 5 个，`choice` 只占位不实现

**决定**：`say` / `act` / `scene` / `wait` / `read`。`choice`（galgame 选项）写进协议版本号标为 reserved，不写实现。

**为什么**：`say/act/scene` 已经覆盖聊天与场景的表达力（生活里人也会"发一条只写动作的话"和"描一句自己在干嘛"）。但一旦有选项，用户就从"想说什么说什么"变成"在给定的框里选"，聊天立刻变成关卡——所以它只能是低频调味品，不是基础机制。

**好处**：`choice` 和"模式切换确认卡片"是同一个机制（引擎停下来问用户一个二选一）。等真要做 `choice` 时，实现一次两处受益。

---

## D6. 用户侧做防抖，且**不做**语义预判

**决定**：规则 + 自适应窗口，0 次 API 调用。不做"每条消息都问模型他说完了吗"。

**为什么**：
- 代价不对称：唯一会犯的错是**早开工**（拿到半句就生成，答偏且半句已落盘难收拾），而**晚开工的代价只是一点延迟**。所以目标是"判断错也没关系"，不是"判断准"。
- 语义预判每条都要带完整上下文调一次模型，成本和正式回复一样贵，收益只是省几秒。
- 判断权交给读得懂语义的那一方：模型可以用 `wait` 事件主动表示"我在等你把话说完"，成本只有几个输出 token。

**自适应用法**：本地统计你自己的连发条数/间隔/句尾标点率。只有一个人用，个性化收益拉满而成本为零——通用产品做不到这件事。

> ### D6 补充（2026-10-07）：防抖是**默认**，不是唯一
>
> 现在多了一个"发送方式"开关（`SendMode`）：**自动（防抖）** 就是上面这一整套；
> **手动（两段）** 里用户按第二次发送键才算"说完了"，防抖完全不参与判断。
>
> **为什么不让手动模式取代它**：两者解决的是同一件事（"他到底说完了没有"），但代价不同 ——
> 防抖**不用多按一次**，但会猜错；手动不猜，但每条都要按两次。这是用户自己的偏好，
> 没有哪个客观更优，所以做成开关而不是替换。默认留在自动那一侧：
> **加开关这件事不该改变任何既有行为。**
>
> 手动模式下代发消息的落点（数据库 + `sentToModel` 标记，以及"上下文排除未推送"那条过滤）
> 是**唯一实现点**，见 [04-changes.md](04-changes.md) 同日的条目。
> ⚠️ 启用那个字段的同时**必须**把老数据标对：库里既有的用户消息全都是 `false`
> （那是个死字段），不迁移的话模型会看不见用户说过的所有话，而且"补推代发"会对
> 每一场老会话凭空起一轮 —— 所以有 `MIGRATION_2_3`（schema 到 v3）。
> `Debounce` / `RhythmLearner` 两个文件在手动模式下**不再参与**开工判断，但仍然活着 ——
> 自动模式还要用，别当死代码删掉。

## D7. 面对面模式是同一会话内的状态转移，不是独立会话

**决定**：会话上的 `mode: chat | scene` 可变；事件带 `mode` 标记；历史是一条线。

**为什么**：
- 用户在门口聊完切回聊天后，模型仍然记得门口那段——独立会话做不到这件事。
- 切换由模型提议（读到"我在门口呢"这类见面信号），服务端校验，**默认需确认**。因为自动切换一旦判错（把玩笑话当成真要见面），体验断裂得很明显，而确认一次的成本极低，这个动作本身也很像真人。

**代价**：面对面模式上下文增长快（每轮可能是聊天模式的 3~10 倍字数）。所以"场景结束压缩成摘要事件"**不是优化，是这个模式能长期使用的前提**，必须和模式一起实现，不能事后补。

---

## D8. 不做图像生成

**决定**：砍掉。也不做语音、不做 Electron 桌面壳。

**为什么**：用户明确说不需要。图像生成是另一条成本线和另一套交互（等待、重生成、存储），混进来会让"像在用微信聊天"这个核心体验失焦。

---

## D9. 从 QQ-agent 只搬三类东西：数据 / 算法 / 提示词文风

**决定**：QQ-agent 是 Node.js，**不能直接复用代码，要移植**。按价值分三类搬：

1. **数据（零风险，最省工作量）**：价格表、搜索提供方、人物卡模板、思考方言表 → 转成 JSON 放进 `assets/data/`，用脚本转，不手敲。
2. **算法（移植 + 移植测试）**：SSRF 防护、按字数排节奏、错误分类与重试、记忆档案结构。
3. **提示词与语言风格（质量核心）**：QQ-agent 效果好，作者自己也归因于提示词。搬的是**思路和反模式清单**（不要客服腔、单条 ≤30 字、不要小作文、分条发送的约束），不是 QQ 群的语境。

**不搬**：OneBot/协议端、群聊逻辑（白名单/响应档位/表情包/拍一拍）、社区功能、市场、Electron 外壳、插件的原型包装层（我们在播放器里实现，更干净）。

**许可**：QQ-agent 是 MIT（Copyright (c) 2026 Kondius）。搬运数据与算法时在新项目里保留版权声明与来源说明。

## D10. 历史不设条数上限；变动区的位置**等上下文压缩时一并重排**

**决定（现在）**：`ChatConfig.historyLimit` 默认 **0 = 不限**，全部历史都注入。
**决定（以后）**：做上下文压缩时，把变动区（摘要 / 记忆 / 刚被打断 / 当前模式 / cue）
从"历史之前"挪到"历史之后"，同时删掉 `← 对方刚发的` 那个行内标记 —— **两件事一起做，不分开**。

### 为什么现在不节流

历史在提示词里本来就很小：真机最长那场会话（153 条）全量约 4500 字符，而稳定前缀
（安全 + 人物卡 + 协议 + 风格 + 记忆规则）就有约 4000 字符。掐历史省下的 token
远不如"模型记得住"值钱。压缩要按 **token 预算**做（近 N 轮原文 + 更早的压成摘要），
**不按轮切**。

反直觉的实测：**放开上限之后每轮反而更便宜了。**

| | 输入 | 命中 | 全价 | 命中率 |
|---|---|---|---|---|
| 旧（40 条窗口） | 5.3k | 4.1k | **1.2k** | 77% |
| 新（全量，第二轮即稳态） | 8.0k | 7.6k | **0.49k** | 94% |
| 新（切换那一轮，一次性） | 7.8k | 4.1k | 3.7k | 52% |

原因：**滑动窗口自己在毁缓存**。窗口每轮丢掉最旧几条，历史段的开头就变了，
于是历史**从来没被缓存过** —— 老口径下能命中的恰好只有稳定前缀
（4.1k token ≈ 6774 字符，两个数对得上）。

### 为什么变动区的位置"现在无所谓、以后要紧"

实测（两轮连续的真实提示词，逐字节比）：

```
上一轮 11695 字符 / 这一轮 11974 字符
共同前缀 11621 字符 = 97.1%
分叉点：正好在历史最末尾 —— 上一轮在 `*瞪了一眼*` 之后写的是
        "   ← 对方刚发的，等你回应\n\n【当前时间】…"，这一轮写的是新的历史行
分段：0 system｜6774 记忆｜6831 当前模式｜6875 历史开始｜11917 当前时间
      → 变动区只有 101 字符，它后面挂着 5042 字符的历史
```

- **常态下已经 97% 命中，挪位置一分钱不省**（那两个块本来就没变）。
- 但变动区在**历史之前**：它一旦真变了（`remember` 落一条、模式切换、被打断、cue），
  清掉的是**它后面的全部历史**（5042 字符 ≈ 3.1k token）。放开上限之后这个代价才第一次
  真实存在 —— 以前历史压根没进过缓存，所以看不出来；而且**历史越长，代价越大**。
- 决定性的理由不是今天的钱（也就分的零头），而是：**压缩必然往变动区里塞摘要。**
  变动区若在历史之前，**每压一次就清空整个历史的缓存**，压缩省下的钱会被自己吃掉。
  所以顺序现在定下来，那个功能才不自我抵消。

**重排后的形状**（内容一字不差，token 数不变，只动模型看到的顺序）：

```
[system] 稳定前缀（逐字节不变）
[user]   ### 之前发生过的事（已压缩）      ← 摘要在最前：它按时间顺序在最前，且两次压缩之间不变
         【你们的聊天记录】头 + 历史行（只追加，行内不插任何每轮变化的东西）
         ### 关于对方，你记得的事           ← "状态"，不是"时间"，所以在时间轴之后
         ### 刚才被打断了
         ### 当前模式
         ### 刚刚
         【当前时间】… / 【现在】…
```

整个提示词因此是**一条严格的时间轴 + 状态 + 指令**：
很久以前（压缩）→ 最近（原文）→ 关于对方我知道的（记忆）→ 此刻（模式 / 刚刚 / 时间 / 指令）。

#### 摘要为什么放在**最前**（2026-10-07 追加）

原来的草案把摘要放在历史**之后**。放最前更好，理由有两条，但**不是**缓存：

1. **时间顺序**。摘要覆盖的是最旧的那一段，理应在原文之前。放后面会让"很久以前"
   出现在"刚刚"之后，模型很容易把摘要里的旧事当成刚发生的（而它唯一的时间线索
   就是位置和标题）。
2. **注意力**。它在中间位置时（草案那样夹在原文和记忆之间）正好落在长上下文最容易被
   忽略的那一段；放最前则与"最近原文"紧邻，两者一起构成完整的"故事"，读完才进状态和指令。

⚠️ **缓存上两种放法完全等价**，不要把理由写成"放前面缓存更好"：
两次压缩之间摘要确实不变，但历史在两次压缩之间是**只追加**的（尾部增长不影响它前面的字节），
所以摘要放在原文前还是后，可缓存前缀都一样长。
真正会清空缓存的只有**压缩那一刻**：原文被替换成摘要、整个位置都平移了，
两种放法都从系统前缀之后全部失效。

⚠️ 摘要**只能放在 user 消息里**，绝不能塞进 system 消息末尾：那会破坏
"系统前缀逐字节相同"这条不变式，也会让 `stablePrefixChars` 这个统计数字说谎
（它是界面和成本口径的依据）。

**风险**：内容没变，但记忆与"当前模式"从记录**之前**挪到**之后**，可能影响模型行为
（项目自己写着"指令离现在越近越管用"，方向上更靠末尾是好的；但记忆落在记录之后，
也可能被当成"刚发生的事"）。**这只能靠真机体感确认，不能靠推理**，所以它必须和压缩
一起做、一起验。

**推翻条件**：如果压缩落地后实测（对比 `usage.cachedTokens`）发现重排没有把
"塌方"消掉，那就说明我判断错了这段的位置关系，应当回退成"变动区在历史之前"。

## D11. 解析"宽进"：一个字符写坏，不该赔掉整轮

**决定**：`ScriptParser` 分四层，从"原样整份解析"一路退到"逐条抢救"，
四层全落空才降级成一条纯文本消息：

1. 原样整份解析（正常输出走这里，一个字符都不动）
2. 定向修补后整份解析（弯引号 / 单引号 / 全角标点 / 多一个冒号 / 少一个逗号）
3. 原样逐条抢救（大括号配对扫描，坏的那条跳过、好的照常）
4. 修补后逐条抢救

**为什么**：模型一次输出就是**一整轮**，而 JSON 是"一个字符写坏 = 整份语法作废"的格式。
真机实测：面对面那个会话 216 条消息里有 **27 条**是"没解析出来、被当成一条纯文本消息发出去"，
用户看到的就是一屏原始 JSON。抽查到的两条（消息 999 / 1002）**真正的坏点只有一个**：
`{ "type": "typing_ms": 2500 }` —— 一个多余的冒号，其余 8 条事件全是好的。
钱已经花了，模型的意图也完全清楚（"这里停 2.5 秒"），赔掉整轮不可接受。

**代价（必须承认）**：宽容会掩盖提示词的退化 —— 第 2~4 层把"模型在瞎写"变成"看起来正常"，
提示词里的问题就不再暴露。所以：

- 每一次修补与折叠都往 `Script.dropped` 里写一条备注，日志「阶段: 解析」里看得见；
- 降级在真机日志里是 **WARN**（`AgentTurnRunner` 按 `script.degraded` 分级）；
- 宽容只用来"少赔"，**不用来"猜内容"**（见下）。

**刻意留的边界：不猜"未转义的引号该在哪结束"。**
`{"text":"他说"你好""}` 只能靠猜来救，而猜错等于**替模型编内容** —— 比降级更糟，
用户会以为那是角色说的话。宁可让它明确坏掉（有测试守着这条）。

**推翻条件**：如果日志里出现"修补层产出的正文明显不是模型写的"（开始凭空造内容），
就把修补层整个关掉，只留"原样整份 / 原样逐条"两层 —— 那两层只决定"收不收这一条"，
永远不改任何一条的正文。

### 附带一条：**历史里的"坏范例"也要清**（2026-10-08 追加）

解析修好之后出现了一个新事实：模型**照样**写 `{ "type": "typing_ms": 1600 }`，
而提示词里那句"它不是一种事件类型"就在上面几行。数了一遍才知道，历史里躺着它自己
以前 **11 次**这样的输出（降级成 `say` 之后原样进了消息表），**范例比规则硬**。

所以宽容解析还不够，**宽容的产物不能当范例喂回去**：`PromptBuilder.renderHistory`
