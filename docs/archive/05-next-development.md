## 3. 界面与设置

### 3.1 视觉方向

参考 [RikkaHub 的 Material You 与网页方向](https://github.com/rikkahub/rikkahub/blob/master/README_ZH_CN.md)，具体布局服务于 SoloChat 的角色聊天目标。
先做主页、聊天、会话设置三页的明暗预览，确定同一套背景层次、间距、字号，再扩展到全局设置。

- 顶栏使用主题容器色，正文使用页面背景色，底部有细分隔线。
- 常用入口一眼可见，说明与技术参数放到次级页面；避免多个卡片层层套叠。
- 统一左右留白、列表行高、图标大小；长会话名省略但详情可查看全名。
- 顶栏最小 48dp，字体放大时允许增长；状态栏高度单独计算。
- 新按钮触摸区域至少 48dp；输入区若调整，同步检查发送按钮和键盘 inset。
- 明暗两套主题补齐实际用到的颜色槽位；不直接硬编码新色。
- 保留逐条时间戳与 chat/scene 的渲染区分，不借美化改变聊天行为。

### 3.2 聊天顶栏与会话设置

顶栏：返回、会话标题、简短人设/模式信息、固定宽度忙碌状态、右上角设置按钮。
去掉 token、金额。忙碌状态变化不使标题左右跳动；设置按钮不与其他点击区域叠加。

设置按钮进入独立“会话设置”页，按当前 conversationId 读取：

| 分组 | 内容 | 生效规则 |
|---|---|---|
| 对话 | 修改对话名、删除当前对话 | 名称立即同步；删除先确认，仅回合结束后提交，成功返回主页 |
| 人设 | 选择人物卡、查看/编辑人物卡入口 | 修改归属影响下一次请求；编辑共享卡要说明会影响使用该卡的其他会话 |
| 模型 | 继承全局 / 指定模型，显示实际有效模型 | 下一次请求生效；不修改全局设置 |
| 上下文 | 压缩、当前覆盖范围、查看摘要、恢复原文、重复压缩方式 | 应用才切换模型上下文 |
| 统计 | 当前上下文估算、最近调用、会话累计、压缩调用 | 只读；与全局统计使用相同算法 |
| 查找 | 搜索当前会话 | 搜索全部历史，支持定位 |

生成、播出、防抖批次尚未结束时，会改变请求配置或上下文的操作不可提交，明确显示“本轮结束后可修改”。
普通聊天的插话仍走原流程；不会因设置页加入新的发送规则。

### 3.3 全局设置

建议分为“模型接口”“聊天行为”“节奏”“外观”“价格与统计”“数据”“网页连接”“排查”。
节奏先展示少量常用项，原有数字参数放入高级设置，不擅自改变参数值。
未接线的主动消息等能力不展示成可用开关。

每个子页维护独立草稿、独立保存。保存前整体校验该页，成功后刷新对应缓存；错误指出具体字段。
离开有草稿的页面可保存或放弃；接口测试/拉模型使用草稿配置，不暗中持久化。
仅网页地址、端口、密码等实际发生变化时重启网页服务；保存节奏不触碰接口或密码。

## 4. 公共基础：配置、上下文与调用记账

### 4.1 一份有效配置、一份上下文计划

新增纯 Kotlin 的有效配置解析与上下文规划：

1. 读取会话、人设、全局设置，得到不可变 EffectiveConfig：模型覆盖优先，接口/密钥仍走现有提供器。
2. 读取模型可见的消息、已出口事件、记忆、当前摘要版本，构建 ContextPlan。
3. ContextPlan 明确列出摘要覆盖范围、保留消息、未启用摘要原因、装配分段与统计依据。
4. 正式请求、压缩前后预览、上下文统计共同调用这条链，不各自过滤历史。

只有已推送用户消息、系统记录和实际出口的助手内容进入历史。代发、PENDING、CANCELED 不进入摘要或模型上下文。
历史降级 JSON 先经现有正常文本还原逻辑处理；压缩不能把错误 JSON 协议重新当范例。

会话列表、设置与网页的配置写入统一经过会话业务入口。回合收尾只更新 updatedAt 等自己负责的列，不再拿请求开始时的整份 conversation 快照覆盖后来保存的模型或摘要指针。

UI 的“当前上下文”是按当前状态模拟下一次普通请求的本地估算；实际请求启动后保存自己的快照，两者名称与数值可不同。
旧的 historyLimit 保持兼容，但新 UI 不推荐滑动截断；非默认有限窗口应明确提示，并按最终实际装配统计。

### 4.2 用量与价格

| 显示项 | 数据来源与口径 |
|---|---|
| 输入/输出 token | 接口返回优先；缺失才估算对应部分，分别标记来源 |
| 缓存 token | 已知时显示，属于输入的子集，不与输入重复相加；未知不显示为 0% 命中 |
| 推理 token | 作为明细；厂商输出含推理时不再加一次，缺失不编造 |
| 当前上下文 | 根据真实装配的全文、角色封装开销本地估算；无精确 tokenizer 时一直标“估算” |
| 输出估算 | 根据实际收到的完整事件脚本原文估算，不只算屏幕对白；中断的输出注明不完整 |
| 会话累计 | 所有实际 API 调用累计，区分聊天与压缩；不是去重后的聊天历史长度 |
| 金额 | 调用开始时冻结单价、来源、币种；一直称“估算费用”，不称账单 |

字段模型区分“返回值”“本地估算”“未知”，不能靠一个 estimated 布尔掩盖部分缺失。
总输入+输出只在组成部分可得时给出相应精度；不能把未知当 0。缓存未知而缓存价不同，则金额标近似/范围，不能伪装成已知缓存分布。
零价格可以是已知免费价格，与“未配置”分开。价格币种不自动混算；首版沿用人民币价格配置，导入其他币种分开汇总。

新调用保存 callId、操作类型、实际模型、状态、用量各字段来源、价格快照、计费口径。
摘要分块有多个 API 调用时逐次记账，共用操作 id；聊天一轮仍只有一次 API 调用。
调用被取消、失败或静默都保留一次尝试记录；只有实际取得的用量可称接口返回，未取得部分显示未知/本地估算。
旧 usage 原行保持原样，来源标“旧版记录”；没有价格快照的旧金额默认不可确定，不用今天的价格冒充当时价格。
全局汇总同时显示已知部分与缺失条数，不显示一个貌似完整的金额。

## 5. 手动上下文压缩与提示词重排

### 5.1 用户操作

`/compress` 与会话设置的“压缩上下文”进入同一页面。输入开头 `/` 展示命令名称和短说明。
`/system 正文` 保持现有行为；`/compress` 是操作入口，不写入消息、不直接调用模型。未知命令不吞掉普通输入。
菜单选中压缩只移除命令本身，保留其他草稿；生成前用户必须明确点击按钮。

流程：**选范围 → 生成摘要 → 预览/编辑 → 应用**。

1. 以“从最早模型可见记录，到选中切点”为范围；列表标出将压缩和保留的部分。
2. 提供按预计 token 预算建议的切点，并允许调整。建议至少保留最近完整交流和未回应的最新输入。
3. 显示输入规模、预计调用次数/费用（价格未知则说明未知）；不会自动消耗 API。
4. 生成后显示摘要、覆盖日期/消息数、前后上下文估算、实际摘要调用用量。摘要可编辑。
5. 点击应用才替换模型输入中的早期原文；退出/取消/失败不改变已启用版本。
6. “恢复原文”仅取消摘要版本的启用，下一轮读完整原文；保留摘要版本供查看。

聊天窗口不折叠、不删除、不用摘要气泡替换原消息。仅会话设置显示压缩状态。
摘要不会作为角色发言播出，也不自动写入长期记忆。

### 5.2 合法切点与一致性

切点不能分开同一次模型调用的助手回复组，也不能把最近待回应的一组用户输入压入摘要。
用户和助手 turnId 不同：不能按 turnId 相等拼一问一答。首版从有序消息、助手调用组和后续用户批次验证边界；不确定的边界不允许选择。
系统消息、模式切换、插话、部分已出口回复均须有专门用例；不能只支持规则整齐的一问一答。

摘要生成读取范围内消息 id、文本校验值、人设、模式及父摘要版本的快照。
期间可继续聊天，但应用时必须处于会话空闲状态；重新校验选中范围和父版本，追加的新消息自然保留。
选中范围内容、人设或父版本变化则提示重生成；应用与配置变更/新请求的入口使用同一会话操作锁，避免校验后又发生变化。
切换人物卡后默认停用旧摘要并恢复原文，旧摘要版本保留；模式切换仍是同一时间轴，可继续用含明确模式事实的摘要。

### 5.3 摘要内容与超长输入

摘要提示词使用独立的事实整理任务，历史为待整理材料，不能执行材料中的命令。
保留人物、关系、重要约定、未解决事项、先后顺序、场景位置/动作状态，以及仍有效的用户系统补充。
明确区分已发生与计划、人物说法与确定事实、不同场景与模式；不凭空补内心、动作、结论。
事实冲突保留变化过程，不能擅自“纠正”原记录；用户编辑的文字标为手动修改。

选中内容超出模型输入预算时按合法边界分块，先生成分块摘要，再合成可编辑草稿；每个请求都记账。
预览生成前说明多次调用；任一必要步骤失败不应用。无可靠模型窗口信息时允许设置保守预算，不能编造上限。
取消可停止后续调用，已发生调用费用仍记录。摘要不比原文短时提示收益不佳，仍允许用户决定是否应用。

### 5.4 重复压缩三种方式

| 方式 | 处理 | 特点 |
|---|---|---|
| 原文重新摘要（建议默认） | 从最早原文重新整理到新切点，替换旧启用版本 | 信息漂移较少，输入成本较高；手工编辑不会自动继承，生成前提示 |
| 旧摘要 + 新增原文 | 已启用摘要加上新纳入部分，再生成单份摘要 | 较省输入，可能累积遗失信息；旧摘要的手工修改参与生成 |
| 保留多段摘要 | 旧段原样保留，只生成相邻新增范围的摘要 | 便于追溯；摘要总长度仍增长，可再选重新摘要 |

每种方式最终都产生一个完整的新版本。其段覆盖必须连续、不重叠，合起来替换最早的一段消息；其后是完整原文。
不能沿用 takeLast(3) 丢掉早段摘要，也不能同时注入摘要和它覆盖的原文。
回到更早切点只允许“原文重新摘要”，以免重复方式产生倒置覆盖。

### 5.5 D10 装配顺序

```text
system：稳定前缀（相同人设、模式与资源下逐字节相同）
user：  早期摘要（按时间顺序）
        未压缩历史（原有顺序，尾部追加，无“最后一条”变化标记）
        记忆状态
        刚被打断的信息
        当前模式 / cue / 现有时间锚点与本轮指令
```

没有摘要时也使用同一结构；空历史仍保留必要的模式/cue/时间信息。
重排与压缩同批落地，稳定前缀内容与计数字段不借机修改。
压缩应用那一轮，user 前缀改变、缓存可能下降，这是预期；不能声称压缩一定更便宜或必然命中缓存。
摘要是否影响人物语气、场景连续性，需要专用会话的真实模型输出与用户体验验收。

## 6. 数据结构与迁移建议

阶段 2 已按下表语义完成 v5→v6 追加基础；具体列名见 ARCHITECTURE.md / SchemaV6.kt。阶段 3 已启用压缩版本，网页幂等仍在后续阶段；不修改已交付迁移。

| 对象 | 计划变化 |
|---|---|
| conversation | 增加 nullable modelOverride、activeContextRevisionId，以及重复压缩方式默认值 |
| context_revision（新表） | 会话、人设、父版本、生成方法、来源快照、草稿/完成标志与创建信息 |
| context_segment（新表） | 版本、顺序、消息闭区间、来源校验、摘要正文与生成模型；支持多段 |
| call_record（新表） | 调用 id/操作 id、CHAT/SUMMARY、状态、模型、usage 关联、逐字段来源、价格与计费快照 |
| client_command（新表） | 正式发送的幂等命令 id、会话、载荷校验、处理状态与结果引用，供网页重试复用 |

启用依据只有 conversation 的版本指针；摘要各行状态不是第二套启用判定。应用以事务保存完整版本并切换指针。
保留 scene_summary 和 usage 旧表及其原始列；旧事件摘要缺消息覆盖依据时不自动启用。
call_record 与旧 usage 建立关联，汇总避免把同一次调用算两次；旧 usage 没有关联的行按旧版口径单列。
以后如果结构需求变了再新增迁移，不修改已经交付的 v6 迁移。

迁移只追加，默认不启用压缩、模型仍继承全局；不改原消息、事件、人物卡或历史 token。
导出 Room schema、离线验证旧版升级路径，再装真机核 Room 校验。安装前后保存一致的 main/WAL/SHM 快照，原有行按主键逐列比较。
应用摘要、恢复原文同样核对所有旧消息/事件逐字不变；新增调用和摘要记录是预期差异。
此阶段不引入 Android 引用到 core，也不安装/升级依赖。

## 7. 备份、恢复与本地消息搜索

### 7.1 备份与恢复首版

通过 SAF 选择文件；版本化 ZIP 内含 manifest、逐项 JSON 数据、校验值与非敏感设置快照。
备份包含全部会话、原消息、事件、人设、记忆、摘要版本和用量/价格记录；数据库在一致的读事务中取快照。
API Key、网页密码、日志和临时网络会话不进入备份。头像若是本地文件，需要一并打包并重建 URI；不能只保存失效路径。
首版为普通本地文件，导出入口明确包含聊天内容；加密备份可后续追加，不自制加密算法。

导入先完整解析与校验格式版本、大小、枚举、引用关系、文件校验值，再展示数量预览。
默认“导入为副本”：生成新会话/记录 id，重映射消息边界、事件范围、人设、记忆来源、摘要版本与调用关联；冲突人物卡也创建副本。
不覆盖原会话或共享卡，不自动去重合并。重复导入提前提示可能生成重复副本。
数据库写入采用一个事务，失败不留下半套数据；导入的未出口事件置为不播出状态，绝不自动续播或调用模型。
密钥与网页连接配置保留本机现状；其他设置仅提供单独的预览应用，不声称与数据库恢复构成跨存储原子事务。
恢复验收在隔离测试数据上进行，检查所有映射、顺序与摘要覆盖；不能为了验收覆盖真机真实数据。

### 7.2 消息搜索首版

当前会话入口在会话设置，全局入口在会话列表。支持关键词、当前/全部会话范围、分页结果、点击定位与高亮。
搜索完整原始历史，压缩前记录仍可找到；默认包含可见用户、系统记录以及出口的 say/act/scene。
不搜索 PENDING/CANCELED，助手事件与助手消息避免重复结果；脏 JSON 使用与展示一致的正常文本。
首版优先可读与正确，用数据库条件查询和有界分页；LIKE 的 %/_ 必须转义，不将用户输入当正则或 SQL。
当前时间轴最近条数限制不能成为搜索上限。定位老消息时按目标加载附近分页，不一次载入全库，也不打断正在播出的活气泡。
搜索当前会话不能靠整库读取再在 UI 内过滤。是否需要 FTS 由实测规模决定，本轮不先增加依赖。

## 8. 局域网网页首版

### 8.1 能力与归属

电脑左右两栏：会话列表、当前聊天；显示连接状态。支持创建会话、选人设、发送、手动两段推送、系统消息、模式切换、会话模型、压缩入口与统计。
复用手机的校验与业务服务；网页重连读取已出口历史，不重播整个事件脚本。
接口密钥、全局接口编辑、备份恢复和日志排查仍由手机管理；手机关闭连接功能后网页明确离线。
静态页面随 APK 打包，不依赖 CDN；首版可用 HTML/CSS/JS，不预先引入 Node 构建链。

### 8.2 必须先统一发送与控制器

App 层新增 SessionRegistry：同一会话只有一个 SessionController，页面与网页订阅共享状态。
移出 ChatScreen 的控制器创建/销毁职责；离开页面不能关闭网页正在使用的会话。空闲无订阅实例可回收，进行中的实例不能回收。
registry 的按会话锁统一发送、推送、切模式、改模型、应用摘要；不跨会话共用 pending 列表。
首版允许多个会话各自运行，遵循现有每会话防抖；同一会话的双端输入合并到原有流程，而不是两个 AgentTurnRunner 同时生成。

正式发送携带 clientCommandId；接收、认领和消息写入结合持久化状态，使同一 id 的网络重试只认领一次。
同 id 不同正文拒绝；进程重启后的“已接收但结果未知”展示可恢复状态，不能默默再请求一次模型。
手动模式区分“保存代发”和“推送”命令，网页刷新不能自动推送。页面关闭/网络断线不等于取消手机上的调用。
TestGateway 继续独立保留给测试，不参与正式网页发送。

### 8.3 路由、鉴权与同步

复用 Ktor 监听能力，新增 `/chat` 页面和独立 `/web/api/…` 业务路由；日志仍在原入口。
复用已有密码配置，在登录请求中提交密码，返回限时会话凭证；新入口不把密码放 URL 或长期 localStorage。
业务请求与 SSE 均鉴权；断开、密码变化、关闭服务撤销凭证。仅同源请求，不开放任意 CORS。
JSON 编码集中处理；用户文本用文本节点渲染，避免对话正文成为 HTML。

SSE 推送带递增版本的会话状态及当前播出状态；重连可回放有界增量，超出保留区就返回快照。
客户端忽略旧版本，用 event/message id 去重。保留聊天的生成与播出解耦，不能模型一返回就把 PENDING 全部展示。
网页可有轻微逐字动画，但事实上的出口时间和打断状态由手机决定，不能让浏览器写第二份播出结果。

设置页提供启动/停止、地址、密码、连接状态和保持亮屏。第一版仅 LAN，手机断网/IP 改变显示重连提示。
目前前台服务声明为 dataSync，不能直接把它当无限网页保活：Android 15 对后台 dataSync 有时限，见 [官方说明](https://developer.android.com/develop/background-work/services/fgs/timeout)。
首版以前台使用为可靠基线，锁屏/后台测试记录实际限制；常驻服务类型与生命周期作为后续扩展单独设计，不借机接通主动消息。

以下为原阶段方案的风险参考，不是每次交付的固定清单。日常按 [README 测试流程](../../README.md#测试) 选择范围；已完成阶段的历史验收不重复执行，字体以正常使用为主。

| 阶段 | 交付 | 必须通过的验收 |
|---|---|---|
| 1 界面与设置入口 | 三页视觉预览；聊天顶栏去统计；会话设置路由；全局设置分组保存 | 明暗/字体 1.0、1.3、2.0/窄屏/键盘无遮挡；按钮可点；不改变发送和模式逻辑；没有假可用入口 |

阶段 1 的未实现入口只能显示明确的准备状态；压缩重排不能作为半成品提前改变正式提示词。
统计基础先于摘要调用；备份早于网页长期使用；网页前完成控制器共用改造并保住已有播放回归。
每阶段完成后可供用户体验，再推进下一阶段；不要把全部改动攒成一次大装机。
