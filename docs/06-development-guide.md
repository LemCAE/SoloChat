## 1. 开发方向与顺序

核心价值仍是“像跟一个人聊天”：同一会话中的 chat/scene、逐条播出、插话、稳定人设与连贯记忆。下一步优先让积累的聊天**能保存、能找回、能长期继续**，之后再把同一套体验延伸到电脑浏览器。

1. 修正错误恢复、记忆范围与操作说明中的误导，为数据读取边界补复现用例。
2. 完成可校验的备份与副本恢复，先建立保护数据的能力。
3. 完成时间轴分页、完整历史搜索与定位。
4. 用独立测试资料验证长会话/长场景压缩，测量本地性能与事实保留。
5. 共享控制器与持久化幂等命令完成后，再接正式局域网网页。

长测的离线材料可提前准备；真实模型长测先估算调用次数与费用，不在日常会话跑百轮测试。

## 3. 修复与改进清单

编号供后续任务与变更记录引用。本文 P1 表示下一批应处理，P2 表示依赖出现时处理。**未经复现的风险不标成紧急生产故障。**

### F1 · P1：错误提示承诺自动重试，业务链路没有兑现

**实施补记（2026-10-21）**：最小修复已落地：提示不再承诺自动重试；请求自身超时以 TIMEOUT/FAILED 收尾，上层取消继续传播并记为 CANCELED。未增加自动重试或显式重新请求入口，未改旧调用记录。

**代码事实**：[LlmError.advice](../core/src/main/kotlin/app/solochat/core/llm/LlmError.kt) 对限流、服务端错误、超时写“会自动重试”。[AgentTurnRunner.run](../core/src/main/kotlin/app/solochat/core/agent/AgentTurnRunner.kt) 遇到 `LlmException` 记失败并返回；[SessionController.startTurn](../app/src/main/kotlin/app/solochat/play/SessionController.kt) 展示错误，不启动业务重试；错误卡只有设置、日志与关闭入口。底层 HTTP 连接恢复不等于业务重试承诺。

**最小修复**：先让提示与行为一致。区分主动取消、网络超时和外层 `withTimeout` 超时；当前外层超时生成 `Canceled`，不要让等待超时只表现为“已取消”。保留旧调用记录，不回填历史状态。

**增强建议**：增加显式“重新请求”，复用已保存输入而非再插一条用户消息，新调用单独记账。明确使用最新上下文还是保存的请求，不暗称为逐字重放。超时不等于服务端未计费，不做不可见的无限重试。

**验收**：先用 429、5xx、底层超时、外层超时替身写红例；修复后提示与实际请求次数一致，失败记录可查，明确重试才新增调用，不复制用户历史。

### F2 · P1：时间轴两类记录读取范围不同

**代码事实**：`SessionController.reloadNow` 及播放投影读取全部 `eventsOf(id)`，消息侧固定 `recentMessages(id, limit = 400)`；[RoomStore.eventsOf](../app/src/main/kotlin/app/solochat/data/db/RoomStore.kt) 先取全量再过滤。[ChatProjector](../app/src/main/kotlin/app/solochat/play/ChatProjector.kt) 的用户/系统内容来自消息，助手可见气泡来自事件。

**推导结果**：超过最近 400 条消息的区域，早期助手事件仍可进入投影，用户/系统记录却可能缺席。这是界面读取边界，不是原记录被删除，也不等于模型历史截断；本轮未在真机制造该现象。

**修复方向**：统一可见时间轴的有界分页和目标定位，两种来源共用显示排序与游标。不能仅把 400 改成更大常数，不能把 UI 分页限制施加到 ContextPlan。

**验收**：至少 401 条混合消息，覆盖用户动作/环境、系统记录、助手、同毫秒时间、早期修复产生的新事件 ID。前后翻页无缺失/重复；搜索能定位老记录；播出新气泡不重置旧记录阅读位置。

### F3 · P1：记忆页说明与共享范围不一致

**实施补记（2026-10-21）**：已去掉字面星号，明确同卡会话共享、通用记忆适用于所有卡，以及未选入本轮的记忆仍然保存。当前没有自动淘汰调用链，已去掉该承诺；本次只改说明，不改记忆查询、排序、保存与删除行为。

**代码事实**：[MemoryScreen](../app/src/main/kotlin/app/solochat/ui/memory/MemoryScreen.kt) 将 `**按人设分开**` 直接传给 `Text`，并写“只有那个对话看得到”。[MemoryDao.all](../app/src/main/kotlin/app/solochat/data/db/Daos.kt) 实际取该人物卡与通用记忆，同卡多个会话可共享；[ContextPlanner](../core/src/main/kotlin/app/solochat/core/agent/ContextPlan.kt) 排序后最多选 24 条。

**最小修复**：去掉字面星号，明确“同一人物卡的会话共享，通用记忆可用于所有人物卡”。区分存储、候选和实际注入，不把未选入本轮称为已删除。页面关于自动淘汰的承诺应核实完整调用链后再保留。

**验收**：独立 A/B 测试卡及同卡两个会话：同卡共享、跨卡隔离、通用可见与说明一致。先检查实际上下文装配，无需为规则测试请求模型，再用真机确认入口文案。

### F5 · P2：离开聊天与未发送内容的生命周期需补证据

`ChatScreen` 创建控制器，`onDispose` 调 `close()`；后者取消防抖、生成与逐字任务。自动模式待认领输入仅在内存，手动代发已落盘。这是现有取舍，不能直接描述成支持后台继续。

补测自动防抖中返回、生成中返回、播出中返回、重建和进程中断。逐项记录输入保存位置、调用是否继续、剩余事件状态与重进表现，检查是否有已显示但未落盘的输入或遗留 PENDING。本轮不把这些风险写成已复现缺陷。

先建立矩阵和红例，再决定保持离页取消还是改为应用级控制器；正式网页必须采用后者。若新增持久化待发送队列，应成为唯一写入源，不能在认领落盘旁再写一份。恢复进程不得自动再收费，未出口内容不得重启后冒出。

### F6 · P2：压缩减少请求长度，不一定减少本地成本

`ContextPlanner.prepareUnlocked` 每次取全模型历史和全事件；启用摘要后仍校验来源指纹。`reloadNow` 每条播完重新投影，事件增长后可能增加读取与排序成本。**尚无本轮性能测量，不能直接声称已出现卡顿。**

先记录数据规模、装配/投影耗时、主线程卡顿与峰值内存；确认瓶颈后再做分页、增量投影或有明确失效条件的校验缓存。不能禁止逐条刷新来掩盖问题，也不能绕过人物卡/历史改变后的摘要回退。

## 4. 阶段 4A：备份与副本恢复

**实施进度（2026-10-21）**：core 层文件协议、引用校验与副本规划已落地，10 条定向测试通过；详细格式与适配要求见 [07-backup-format.md](07-backup-format.md)。尚无 Room/SAF 或用户入口，阶段 4A 未完成。当前协议小步排除设置与头像文件；完整数据链路完成后再扩展，不把其余目标提前标为已实现。

### 4A-1 交付范围

沿用 05 §7.1：SAF 文件选择、版本化 ZIP、manifest、JSON 与校验值、预览后导入副本。保留当前会话，不提供整库覆盖与自动合并。

包含会话、原消息、事件、人物卡、记忆、旧摘要、上下文修订/段、调用与用量/价格快照；排除密钥、网页密码、日志与临时连接凭证。数据库取一致快照，文件编码/写出放在事务外。非敏感设置独立预览应用，不声称数据库与 DataStore 跨存储原子恢复。

网页命令表未来若有数据，必须明确其运行态/审计用途：**导入不得恢复执行权限或重放命令**。初版建议不恢复为可执行任务，清单写明排除规则。本地头像等文件若纳入，应打包实际内容，不能只保存失效 URI。

### 4A-2 当前代码额外要求的边界

1. **摘要指纹含旧身份。** [ContextRevision.kt](../core/src/main/kotlin/app/solochat/core/model/ContextRevision.kt) 对完整 Message/Event 序列化做指纹，人设也有校验。先验证原包，再重映射消息/事件、人设、父修订、段边界并重算指纹和段校验，最后执行现有 `validateSegments` / `validateCompressionSource`。不能只替换外层 ID，也不能关闭校验。原包中本来失效的摘要不得被重算“洗成有效”：保留文本、停用并说明原因。
2. **导入代发可能自动推送。** `SessionController.open` 在 AUTO 下调用 `pushUnpushed`。仅取消未播事件不够：需导入后的待发送隔离状态或等价机制，保留 `sentToModel=false` 语义，首次打开也不请求模型，明确推送才解除。不能靠改全局发送模式或伪造已发送规避。
3. **部分悬空来源是合法历史。** `RoomStore.deleteConversation` 保留记忆、调用和用量，它们的来源会话可能已删。校验要区分允许缺失的审计来源与必须存在的摘要关系；保留原来源标识，不能误指向本机已有会话。
4. **JSON 内也有引用。** 映射须覆盖 `sourceSnapshotJson`、调用 `detailJson` 内历史 ID、`usageId` 和父修订等。`turnId` 是历史回合标识，不当表主键随意重编号；保持消息/事件回合对应和相对顺序。内置人物卡导入副本不能覆盖本机默认卡。

### 4A-3 拆分与验收

| 小步 | 代码归属建议 | 完成判据 |
|---|---|---|
| 格式与导入计划 | core 新增纯数据校验/映射模块 | 未知版本、损坏校验、缺必需引用、重复 ID、过量展开/路径穿越均在写库前拒绝 |
| 一致导出 | app/data 与 Room 事务适配 | 原库不变，清单与内容一致，失败不报成功 |
| 副本导入 | Room 单事务写入 | 任一步失败全回滚；原记录不变；重复导入提示副本 |
| SAF 页面 | 设置增加数据入口 | 中文文件名、取消选择、不可写位置、损坏包与预览取消均可恢复 |
| 恢复后使用 | 时间轴/压缩/统计联验 | 顺序正确，摘要状态正确，金额不按现价重算，打开不续播/不请求模型 |

合成资料先做导出→导入→再导出，比较语义与引用完整性，重映射后的副本不要求字节相同；真机原有记录仍须双份一致快照逐列核对。导入账目会增加副本，应标识来源并明确统计是否纳入，避免重复导入被误认成新增消费。

## 5. 阶段 4B：完整历史、搜索与定位

F2 与搜索一起设计，按“时间轴查询→分页→搜索→点击定位”分步交付。

- 定义稳定定位键，至少含来源类型与 ID，message.id 与 event.id 不能混为一类。沿用可见投影的确定性排序，处理同毫秒时间，不仅靠插入 ID 判断发生顺序。
- 助手结果以出口事件为准，不再返回 assistant 消息副本；隐藏事件与记忆不进聊天搜索。用户/系统沿用显示语义；代发若可搜到，标明未推送，不因此送入模型/摘要。
- 当前/全局范围都查完整数据库历史；正确转义 LIKE 的 `%`、`_` 与转义符。先用有界查询，是否需要 FTS 由实测决定。
- 结果提供会话、摘要、定位键；按目标加载前后文，提供高亮和返回最新。搜索不请求模型、不改摘要或记忆使用次数。
- 翻旧记录时，新回复只提示有新消息，保持滚动锚点；仍遵守 live 气泡交接，不重播旧事件。

**验收集**：空词、中文、emoji、同文多次出现、LIKE 特殊字符、已压缩记录、超出 400 条窗口、chat/scene/system 混合、取消事件、播出时翻页、点击前目标被删；可恢复失败，不丢草稿。

## 6. 长会话与压缩验证

以下规模为**建议设计，尚未实测**。

1. **离线层**：100 轮以上、上千事件的合成材料，包含系统补充、否定偏好、未兑现计划、插话、模式切换、重复短句和人物卡变化。三种压缩均验证前缀覆盖无重复/遗漏、原记录不变、失效回退、编辑应用与恢复。
2. **模型层**：新建 `TEST-LONG-<日期>` / `TEST-SCENE-<日期>` 与独立人物卡。先短样本核脚本及费用，再分段长测；固定对照组记忆条件，避免自动记忆掩盖摘要丢失。测试网关不走正常播放和助手历史写入，不能拿连续 send 当完整多轮 UI 验收；应走正常控制器或有等价落盘语义的专用适配器。
3. **质量层**：记录事实正确/缺失/冲突、否定反转、计划误当已发生、场景位置/未完成动作、重复回复。实际请求与下一轮回答都要看，“摘要有这个词”不等于模型会正确用。
4. **成本与性能层**：分别记摘要调用成本、后续估算/返回 token、缓存字段、本地装配耗时。短摘要不必然降低总费用，价格或缓存字段缺失就保留未知。

按覆盖一致性、事实保留、角色语气、成本、本地性能分别交付，不笼统称全部通过。记录资料版本、模型配置、调用记录、失败例和保留的测试会话；正文私有证据在忽略目录，文档只写脱敏结论。

## 7. 阶段 5：正式局域网网页

沿用 05 §8 的前台使用基线，备份可用后再推进；先业务基础，再网页外观。

1. 应用级 `SessionRegistry` 按会话持有唯一控制器，手机与网页订阅共享状态、提交命令。页面退出不释放工作实例，空闲可回收；会话锁不跨网络等待。
2. 持久化 `clientCommandId`、正文校验、处理状态，区分发送/保存代发/推送/切模式。同 ID 同文返回同结果，异文拒绝；断线/刷新/重启不静默重复收费，未知结果显式显示。
3. 独立业务路由，不复用 `TestGateway.send`。SSE 状态带版本，重连取快照或有界增量，手机决定出口事实，PENDING 不提前展示。
4. 业务/SSE 均鉴权，改密码或关服务撤销会话；新入口不把长期密码放 URL 或 localStorage。正文按文本渲染，静态资源随 APK 提供。
5. 先验列表、选择会话、双端发送、手动两段，再接模型、模式、压缩与统计，复用手机校验。

验收含同时输入、重复点击、同 ID 异文、断网、刷新、请求中杀进程、多会话、手机返回与锁屏。后台可用性只按实测描述，实施时再核目标 Android 版本官方限制，不沿用旧平台行为推测。

## 11. 追加：GitHub 版本状态与更新下载（2026-10-22，待实施）

用户要求加入版本检查与拉取更新。已核对当前远端为 `LemCAE/SoloChat`，发布工作流在 Release（含预发布）发布后生成并上传签名 APK。更新功能安排在备份导出/副本恢复之后、历史搜索之前，先能保护资料，再交付覆盖升级。

首版流程：设置新增“关于与更新”→ 手动检查 → 展示当前/远端版本、正式版/预发布、发布日期和更新说明 → 用户点击下载 → 展示进度、取消与失败重试 → 下载完成后交给系统确认安装。默认正式版，可显式启用预发布；不在聊天过程中弹出更新，不静默安装、不自动改数据库。网络失败与限流显示检查失败/可重试时间，不显示成“已是最新”。

| 小步 | 实施范围 |
|---|---|
| U1 · 查询与版本状态 | 从固定仓库的 GitHub Releases API 读取发布信息与 assets；稳定渠道过滤草稿/预发布，测试渠道包含预发布。按版本语义比较，不使用字符串排序，不把 debug 后缀当远端预发布渠道；处理未发布版本、无安装包及无可比较版本。保留发布页入口与本次检查状态，重复点击复用正在进行的检查，不新增后台轮询 |
| U2 · 拉取安装包 | 只提供当前发布对应的 Android APK；使用 GitHub 返回的下载链接，不把模型 Key 或日志网页密码带给 GitHub。固定同一版本/asset 的下载任务，显示进度/取消；网络失败可以重试。下载完成才显示“安装”，需要时可打开发布页手动下载 |
| U3 · 系统安装与资料边界 | 检查下载 APK 的包名、版本码和签名是否支持当前安装的覆盖更新，再启动 Android 系统安装确认；按系统提示处理安装来源授权。当前 debug 为 `app.solochat.debug`、发布包为 `app.solochat`，不同包名提示独立安装及数据不自动迁移，不能声称会覆盖保留原 debug 数据。覆盖升级前提供备份入口，不自动执行恢复 |

**发布状态边界**：当前流程先发布 Release、再构建上传，API 中可能暂时没有 `app-release.apk`。此时显示“版本已发布，安装包尚未就绪”，保留稍后手动刷新/打开发布页，不伪造下载地址、不直接判断构建失败，也不向 App 暴露 Actions Secrets。安装后的可升级性以包内版本码与签名为准；同版本重发或版本码回退不能仅靠 tag 判断。

**必要检查**：版本比较、渠道过滤、缺失 APK 和失败状态用定向用例；下载/系统安装在功能接齐后用同包名、同签名的专用安装验证。现有 debug 包不直接切换覆盖为 release，真实资料不用于升级试错。不增加日常全量重跑或哈希/取证流程。

接口依据：[GitHub Releases API](https://docs.github.com/en/rest/releases/releases)、[Android PackageInstaller](https://developer.android.com/reference/android/content/pm/PackageInstaller)。以上是计划，尚未实现在线检查、下载或安装。
