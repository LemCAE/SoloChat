# SoloChat 实施方案

> 这份文件是**批准的方案原文**，写在动手之前。落地之后的实际情况、偏离与后续步骤见文末的
> 「实施状态」一节。设计取舍的原因见 [01-decisions.md](01-decisions.md)。

## 0. 三个已定的决定

1. **形态**：Android 原生 App（Kotlin + Jetpack Compose）；局域网网页版作为后续阶段，架构上预留、不先做
2. **服务端常驻 = App 内的前台服务**，不是外部服务器。所有逻辑跑在手机上，离线可用、隐私自持；"常驻"由前台服务 + 常驻通知实现
3. **技术栈**：Kotlin + Compose；Room 持久化；EncryptedSharedPreferences 存 API Key

## 1. 目标与成功标准

做一个**像在用微信一样在跟一个人聊天**的 Android App：不接平台、不用账号、只填模型 Base URL + Key。

验收（真机端到端）：

- 装 App → 填接口地址和 Key → 拉模型列表选一个 → 开始聊，逐字出现、对方有"正在输入…"
- **你连发三条半句话，它等你说完才回**，不会对着半句抢答
- 它的回复**分 2~3 条独立气泡**，每条长短和间隔都像真人在打字，不是一次性贴一篇小作文
- 你说"我到你楼下了" → 它提议"见面"，你点确认 → **同一个会话里**切成面对面剧本样式，之前聊过的内容它依然记得
- 关掉重开、隔一天再打开，历史、人设、记忆都在；用量页能看今天花了多少钱
- 全程没有把 Key 或聊天内容发给模型 API 之外的第三方

## 2. 事件协议（整个系统的中枢）

**一轮 = 一次 API 调用**，模型返回一段带时序的事件脚本，引擎负责播出。

| 类型 | 含义 | 聊天模式渲染 | 面对面渲染 |
|---|---|---|---|
| `say` | 一条消息 / 一句台词 | 独立气泡（一条一行） | 角色对白 |
| `act` | 动作、神态（自己） | 斜体小字一行 | `*她把头发别到耳后*` |
| `scene` | 环境旁白（无人称） | 居中灰字，少用 | 居中灰字，主力 |
| `wait` | **本轮不回复** | 什么都不播，推进时间 | 同 |
| `read` | 已读回执 | 一个已读标记 | — |
| `remember` | 顺手写一条长期记忆 | **不播出** | 同 |
| `choice` | **保留，不实现** | 预留槽位 | 预留槽位 |

> 落地时的调整：原本只规划了 5 种，实现时加了 `remember`。理由是"记忆写入"如果做成工具调用，
> 会多一次完整前缀往返（贵且慢），而它根本不需要返回值。做成脚本里的一条事件，成本只有几个输出 token。
> 详见 01-decisions.md。

事件字段（协议侧）：`type` / `speaker` / `text` / `gap_ms` / `typing_ms` / `reason`；
脚本级：`next_mode` / `mode_reason`。

## 3. Agent 回合流水线

```
收到用户消息
  └─ RF1 防抖（规则引擎 + 自适应，0 次 API 调用）
       └─ RF2 上下文装配（系统前缀 + 人物卡 + 记忆 + 场景摘要 + 近期原文）
            └─ RF3 一次调用（流式收原文）
                 └─ RF4 解析成事件脚本
                      └─ RF5 播放器排程播出（打字指示 → 逐条播出 → 落盘）
                           └─ RF6 落盘：逐事件写状态，计算用量与成本
```

防抖的档位与阈值（聊天/媒体/分句/短句/新一轮/硬上限 30 秒）见 `core/.../Debounce.kt`；
节奏（每字 700~1100ms 各自随机累加，与模型给的 `gap_ms` 加权混合）见 `core/.../Pacing.kt`。

## 4. 模式切换

会话上的 `mode: chat | scene` 可变；模型在输出里带 `next_mode` 提议；服务端按
`自动 / 需确认 / 关闭` 校验，**默认"需确认"**；**直接发一条消息即视为拒绝**（卡片不阻塞输入）；
切换点写一条系统消息进历史（模型才知道"我们见面了"），界面上打一条居中分隔行。

## 5. 工程结构

```
SoloChat/
  core/                      纯 Kotlin JVM 模块，不含任何 Android API
    model/  protocol/  agent/  llm/  playback/  prompt/  ports/
  app/                       Android 模块
    src/main/kotlin/app/solochat/
      data/         Room 实体与 DAO、Store、加密 Key、价格解析、提示词加载
      play/         SessionController（防抖/抢占/播放编排）、ChatProjector（投影）
      ui/           Compose 界面（聊天、会话列表、设置、人物卡、记忆、用量）
      service/      前台服务（常驻 + 主动消息检查）
    src/main/assets/
      prompts/      提示词分段（00-safety / 10-protocol-* / 20-style-* / 30-memory / 40-proactive）
      data/         从 QQ-agent 转出的数据（价格表 / 搜索清单 / 人物卡模板 / 思考方言）
  tools/            下载 Gradle、生成 wrapper、一键构建脚本
  docs/             本方案与设计决定
```

## 日志（第二轮反馈加的）

第一轮交付时**一条日志都没有**，导致"模型怎么老回一个字""消息为什么一次性放出来"这类问题
完全没法定位，只能靠看截图反推。所以补了一整套：

- **`core/log/Log.kt`**：内存环形缓冲（600 条），带版本号与级别，`StateFlow` 供界面订阅。
  **不落盘** —— 用户明确说"流式的，不用保存"，而且提示词里有全部对话内容，写磁盘是隐私风险。
- **注入式 sink**：`core` 是纯 JVM 模块，不能出现 `android.util.Log`（否则测试全跑不起来）。
  所以 core 只暴露 `LogSink` 接口，由 App 侧注入 `AppLogSink` 打到 logcat
  （`adb logcat -s SoloChat/模型 SoloChat/编排`），超长内容主动分片而不是被 logcat 截断。
- **日志页**（`ui/logs/LogScreen.kt`）：标题栏直接显示版本号，按 tag 过滤（全部 / 模型 / 编排 / 启动）、
  最新在上、隐藏 DEBUG、可关"记完整正文"、长内容可展开、单条可复制、可"复制全部"。
  入口三个：会话列表菜单、设置页「排查」区、出错卡片的「看日志」。
- **打点位置**：用户发送与防抖判定、认领批次、请求参数与**完整提示词**、模型原始输出与耗时、
  解析结果（事件数 / 降级 / 丢弃 / 模式提议）、**播出时间线逐状态**、演出结束与交付时间。

## 提示词：装配没问题，是示例在示范

"一直回在"的怀疑对象本来是提示词装配。为此加了 `PromptBuilderTest`（11 条），
它把**装配好的完整提示词打印出来**，不连真机就能审。结论：

- 段落顺序正确：安全规则 → 人物卡 → 协议 → 风格 → 记忆 → 当前模式 → 历史
- 稳定前缀逐字节稳定（289 字符），记忆/摘要/历史都在前缀之后 → KV 缓存能命中
- 占位符 `{{persona_name}}` 全部被替换
- `remember` 与已取消的事件**都不进上下文**（各有一条测试钉住）

所以不是装配 bug。真正的原因是**我写的 few-shot 示例在示范那个词**：
格式例子里用了"在的""怎么了？"，而输入又是"在干嘛"，模型照抄了。
改法是两条：换掉示例文本（用"刚洗完澡/你那边下雨没"），
并加一条显著提示「例子只是格式示范，不是答题模板，别因为例子里出现过某个词就反复用」，
同时在分条规则后加一节「反复读（很容易犯）」。

## 日志网页（第三轮反馈加的）

"能不能把日志开放到网络端口" —— 能，而且这解决了第一轮就存在的一个痛点：
手机上翻日志要解锁、进页面、长按复制，再想办法传到电脑上看。

实现（`data/logweb/`）：

- **`LogWebServer`**：Ktor CIO 内嵌服务。`/` 给日志页面，`/api/logs` 给 JSON
  （支持 `?since=<seq>` 只取增量，所以每秒轮询只传新条目，不会每次重传 600 条），
  `/api/health` 探活。
- **`LogViewerHtml`**：内联的单个 HTML。暗色等宽、每秒增量拉取、按 tag 与级别过滤、
  关键词搜索、暂停、清屏、下载、复制单条/全部、长内容折叠展开。
  标题栏显示版本号与连接状态。**不依赖任何外部资源**，断网也能用。
- **`LogJsonCodec`**：JSON 编码单独成文件，因为它是纯函数、可在普通 JVM 测试里跑，
  而它恰好是整个功能唯一的"必错点"。

### 安全：这块不能将就

日志里有**完整提示词和全部对话内容**，所以：

| 规则 | 为什么 |
|---|---|
| **默认关闭** | 开着就等于在网络端口上暴露日志 |
| **默认只监听 `127.0.0.1`** | 要 `adb forward` 或在手机自带浏览器里看；不需要密码 |
| **开局域网必须先设密码** | 两条同时满足才允许启动，否则保存被拒并给出原因。同 WiFi 下任何人都能扫到端口 |
| **密码即凭证**（`?t=密码` / `Bearer` / `X-Log-Token`） | 用户自己设的、记得住；随机 token 跨设备反而要"先找到那串字符" |
| 不做 HTTPS、不做用户系统 | 自签证书在手机上装的麻烦远超收益 |

界面上把这三条讲清楚了（不是干巴巴一个"允许局域网"），因为这是"泄露全部聊天记录"
和"方便排查"之间的取舍，用户必须看懂再决定。

### 一个绕了弯的技术点（记下来省得再踩）

`routing { get("/") { call.respondText(...) } }` 这套 DSL 里，**`call` 编译不过**
（"Unresolved reference: call"）。我试了三种写法都不行，最后 `javap` 才看清：
路由 lambda 的接收者是 `PipelineContext<Unit, ApplicationCall>`，
`ApplicationCall` 在**类型参数**位置，所以只有 `context` 是显式可用的。

最终改成**绕开 DSL、直接挂在路由管线上**：

```kotlin
intercept(ApplicationCallPipeline.Call) {
    val call = context        // 毫无歧义
    when (call.request.path()...) { ... }
    finish()                  // 不调它请求会挂住
}
```

好处是路径匹配一眼能看懂，少一层抽象，将来换 ktor 版本也更不容易坏。

### 测试抓到的第二个真 bug（emoji）

`LogJsonCodecTest` 写完第一次跑就报：

```
中文与 emoji 往返正确 FAILED
```

原因是我的转义函数"见到代理项就替换成 U+FFFD"。但 emoji 与很多 CJK 扩展字
在 UTF-16 里就是**高代理 + 低代理**两个 char —— 于是**所有 emoji 都会变成 `�`**。
只有**落单的**代理项才是坏数据。修法是用 `isHighSurrogate` + 检查下一个字符
是否 `isLowSurrogate` 成对处理。

这条特别值得记：错误方向的直觉（"代理项 = 坏字符"）很自然，而症状只在有 emoji 时出现。

## 真机日志定论的三件事（第四轮反馈）

用户把日志导出来贴给我，一次解决了三个悬了很久的问题。**这轮把上一轮做的日志
变成了实际收益** —— 前两轮的猜测有一半是错的。

### ① "一次性放出再重播"：在渲染层，不在引擎

日志的逐状态时间线证明播出**完全正确**：

```
13.136 状态=阅读 event=17   → 等 734ms
13.876 状态=打字 event=17   → 等 110ms
13.992 状态=播出 第 1/2 条「哟」
13.993 状态=间隔 event=18 等 3604ms
17.601 状态=打字 event=18   → 等 880ms
18.490 状态=播出 第 2/2 条「今天怎么想起我了」
```

真因是我在 `liveFor()` 里把**全文**塞进 `ChatItem.Live.text`，
而界面做逐字效果的 `typewriterChars` 要等 `LaunchedEffect(live.key)` 重启后才归零。
中间那一帧就是"全文一次性冒出来"，紧接着动画从头重播。

修法：**把"已显示字符数"放进引擎给的状态里**（切条时置 0），界面只渲染
`take(visibleChars)`，不再自己对齐时序。这样新条目第一帧就是从空开始长。

### ② 用户气泡在模型思考期间不显示：落盘与清空之间有空白期

`claimPending()` 里有一句 `pendingItems = emptyList()`，而**落盘在认领之后**
（`persist()` 是挂起操作）。所以从"清掉待处理气泡"到"那条被 `reload()` 读出来"之间，
界面是空的 —— 那正是模型思考的一秒多：

```
15:12:02.569  认领批次 → pendingItems 清空
15:12:02.589  请求发出
15:12:03.751  开始播出（此时才 reload）
```

修法：待处理气泡**留到对方第一条话开始播出为止**（`clearPendingBubbles()` 的调用点
从认领挪到 `playEvents`）。这样"我发出消息"到"对方冒出回应"全程都看得到我那条。

### ③ 语义混乱：照搬 QQ-agent 的输入格式

用户给了 QQ-agent 实际的请求体（`exampleInput.txt`），对比后发现我丢了三个关键设计：

| QQ-agent 有 | 我原来 | 后果 |
|---|---|---|
| 每条消息带时间戳 `[10-07 09:04]` | 无 | 分不清"刚才"和"很久以前"，读不出"这么晚还不睡" |
| 自己说的话标「我：」 | 靠 `role=assistant` | 模型对自己的输出"读过就算"，容易重复自己刚说过的话 |
| 末尾【当前时间】锚点 | 无 | "明天要上课""国庆最后一天"这类话没有依据 |

这三样全是**语义锚点**，缺了就"听不懂人话"。现在都补上了：

```
【你们的聊天记录】按时间排序，你的发言标为「我：」，对方标为「对方：」
[10-07 09:04] 对方：在干嘛
[10-07 09:05] 我：在
刚吃完饭
[10-07 09:06] 对方：哦   ← 对方刚发的，等你回应

【当前时间】2026-10-07 15:19（周三）
【现在】接着上面的记录，用 JSON 输出你这一轮想说的话。
```

另外学到一条：QQ-agent 把**整份历史放进一条 user 消息**（而不是 user/assistant 交替），
模型只需要回答"接下来我说什么"，归属最清楚。这也照做了。

顺带一个数据点：日志里 `usage: 输入 2515 / 缓存 2304` —— **91.6% 缓存命中**，
说明稳定前缀那套设计是生效的。

### ① 参考转储证实了划分方式（但我的实现已经对了）

QQ-agent 的实际划分：

| | system | user |
|---|---|---|
| 内容 | 全部**规则**（安全/工作方式/反AI味/主体性/工具/技能） | **人物卡** + 引导说明 + 【已读信息】+【未读信息】+【当前时间】 |

**人物卡在 user 侧、规则在 system 侧。** 我在上一轮加的"时间戳 + `我：` + 【当前时间】锚点"
方向与此一致；差别只是我把人物卡放在 system 里。这一点进一步观察，见文末"后续观察"。

### ② 语义问题：实测已经正常了

用接口跑了完整多轮：

```
我: 嗨喽                →  哟，稀客
我: 今天有点累           →  咋了这是 / 不行就躺会儿，别硬撑
我: 你觉得我应该干嘛      →  累了就躺着呗 / 别刷手机 越刷越累
```

`算了不说了` 被正确理解为"不想细说"并接住（没有追问、也没有跑题），
上下文连贯、无重复。缓存命中 **2432/2595 = 93.7%**。所以上一轮的时间戳 + 锚点修复是有效的。

### ③ "瞬时重复"：真机截图抓到，根因是状态更新不原子

`uiautomator dump` 抓到的屏幕文本里，"在，刚没顾上看手机"出现了两次
（"累了就躺着吧，别折腾了"夹在中间），但同一时刻 `/api/history` 返回的 14 条**完全干净**，
模型原始输出也只有 2 个事件 —— **所以重复只存在于界面，是渲染层的一帧**，下一帧就消失。

根因：`playEvents` 里先设 `live = 第 N 条开始播`，**然后**才调 `clearPendingBubbles()`，
而它内部触发 `reload()`。此刻第 N 条**已经落盘**，于是同一内容同时存在于两处：
`items`（reload 读出来的正式条目）与 `live`（还没挪走的活气泡）。

修法：把"投影结果"与"live 交接"放进**同一次 `_state.value = ...`**，
并且当 live 指向的事件已经进 items 时把它置空。状态只有一个写入点，
就不存在"某个中间状态两边都有"的窗口。交接动作也挪到 `runPlayback` 开头（挂起上下文）。

### ④ 【我引入的新 bug】重启后凭空冒出一堆对方的消息

装新包时 App 重启，之后聊天记录里**凭空出现 7 条助手消息**（数据库里
`15:48:14` 有 7 条、0 条用户消息），内容和 4 分钟前一模一样。启动日志给出了答案：

```
15:48:13.986 [启动] SoloChat 启动
15:48:14.142 [启动] 启动收尾：清理残留未播出事件 7 条
```

那 7 条是上一轮**已生成、还没播完**的助手事件。上一轮为了让用户气泡不消失，
我把助手事件提前落盘（标记 `PENDING`）；进程被重启后 `sweepUnfinished` 把它们标成了
**`INTERRUPTED`** —— 而 `INTERRUPTED` 的语义是"说了一半"，也就是**"说过"**。
于是重启后它们全部出现在聊天记录里，而用户从没收到过。

修法：孤儿事件一律标 **`CANCELED`（当没说过）** —— 那才是事实。同时 Room 的严格模式
还抓出这个 UPDATE 里 `deliveredAt` 参数已无用，一并去掉。

> 这条特别值得记：**为了修一个观感问题（气泡消失）而提前落盘，引入了数据语义问题
> （未播出的事件被当成已播出）**。凡是从"界面好看"出发的改动，都要回头检查
> 它有没有动到领域语义。

### ⑤ 接口自身的 JSON bug

`/api/send` 第一次调用报 `unexpected character: :` —— 我手写的 JSON **漏了 `bubbles`
数组的闭合括号**。这是第二次在同一个地方栽（第一次是 emoji 被替换成 `�`）。

所以把响应渲染抽成纯函数 `ResponseJson`，并用**真实解析器**写了 12 条往返测试
（结构闭合、`null` 不被写成字符串、内嵌 JSON 转义、控制字符、emoji、未配对代理项、
NaN/Infinity 落成 null）。测试当场又抓出我断言里写死了 `Double.toString()` 的格式
（0.0005 会写成 `5.0E-4`，那是合法且最短的精确往返表示）—— 改成断言解析回来的**数值**。

## 后续观察（暂不改）

### 说话的"积极性"：一个旋钮，不是两个参数（想法，2026-10-07 记录）

用户提出，两个现象其实是**同一个旋钮的两端**：

- 面对面时一轮能说的东西比聊天多（有动作、有环境、有台词），条数上限显得紧；
- 但也会有**抢着不让对方说**的时候（"一直在逗人家"，一轮把自己的话全说完）。

**先说清现状**（2026-10-07 核对）：条数限制**全在提示词里，代码一侧没有任何上限** ——
`ScriptParser` 只夹时间值（`gap_ms` / `typing_ms`），事件条数一条都不丢。
所以放宽它是纯提示词改动，零代码。

但现状里有**三处数字互相打架**，这才是真问题：

| 位置 | 说的是 |
|---|---|
| `10-protocol-chat.txt` | 普通回话 1 条，**最多 4 条**（同一段又写"4 及以上条"只在该讲故事时） |
| `20-style-chat.txt` | 默认 1 条，**最多 2 条** |
| `10-protocol-scene.txt` | 一轮 **1~4 个事件**（事件含 act / scene，不等于"几句台词"） |
| `20-style-scene.txt` | 只约束环境"最多一到两句"，台词没有数字 |

同一模式下"最多 4 条"和"最多 2 条"同时出现在稳定前缀里，**谁赢没人知道**。

> **2026-10-07 已处理（数字部分）**：数字收成**一处** —— 只写在 `10-protocol-*.txt`，
> 风格文件改成指路。聊天统一取 **4**；面对面 `act` **1~5**（必要时更多）、
> `say` **最多 8 句**、`scene` **最多 1 句**。同时加了"最后一条把话头递回去 /
> 不要自问自答"的行为约束（见 [04-changes.md](04-changes.md) 同日的条目）。
> **下面说的"积极性"旋钮仍然没做。**

#### 三个可选落点（按代价排序）—— 指"积极性"这个旋钮本身，不是上面已经改好的数字

1. **纯提示词**（0 代码）：在风格文件里写成"整体偏多/偏少"这种定性描述。代价最低，
   但**没法按人设/会话分别调**，而且它是"全局默认"，改了就所有人设一起变。
2. **人物卡字段**（动 `PersonaDocument` 的解析与导出 + 人物卡编辑器）：每张卡一个默认积极性。
3. **会话级覆盖**（`Conversation` 加一列 + 会话设置入口）：唯一能让"这一场我想被少撩一点"当场生效的地方。

#### 设计这个功能之前必须先知道的三件事

1. **只能有一个旋钮。** 别做成"条数上限"+"抢话抑制"两个参数 —— 它们会互相打架。
   它该同时管：一轮里能说多少、**跨轮**什么时候主动开口。
2. **跨轮那一半已经有基础设施**：`40-proactive.txt`、`Conversation.proactiveCooldownUntil`、
   三个设置项（开关 / 静默多久 / 冷却）、`AgentForegroundService.checkProactive()`。
   所以"积极性"应当和主动消息**共用一套语义**，而不是新开一个概念。
   （注意 `checkProactive()` 现在只发通知，用的是硬编码的空闲阈值，设置里那三个值还没被读。）
3. **它不能进稳定前缀。** 积极性一旦可调，提示词里那段字就会变；而稳定前缀必须逐字节不变
   （KV 缓存 + `stablePrefixChars` 口径）。**它只能放变动区**（和记忆、摘要同一类）。
   这一条是设计前必须知道的，否则做出来会把缓存打没。

### 模型在一轮里重复说同一个词

真机日志抓到一次：用户连发两次"嗨喽"，模型两次都用「哟」开头，界面上看起来就是
同一个气泡上下重复。已做两件事：提示词里加了"不要用上一轮用过的开场词"，并在
`AgentTurnRunner` 里加了一层保守的重复抑制（丢掉落盘前与**上一轮**助手消息完全相同的
短 `say`，一轮被清空则保留原样）。

但这条**先按观察处理，不作为定论**：用户反馈"一会儿就消失了"，可能是模型偶发。
如果再复现，看日志里的「重复抑制」行就能知道是模型的问题还是抑制过头了。

### 已经排除的原因（"一次性放出再重播"）

- 没有两处播放器（`Player.plan` 只在 `playEvents` 里调一次）
- 没有提前 `reload` 把事件变成历史条目（`runPlayback` 结尾才 `reload`）
- 播放队列没有被重复消费（`typewriterJob` 只启动一次）
- `LazyColumn` 的 key 不会冲突（用户条目与事件条目的 id 前缀不同）
- 分段发送不等于多次模型调用（一轮 2~3 条只是一次调用的多个事件）
- **播出时序本身没问题**（这一条由真机日志证实：每步之间 0.8~3.7 秒）


## 真机反馈修掉的 bug：用户消息成对出现

装机试聊后反馈：**自己发的每条消息在界面上显示两遍**，而对方的回复只有一份。
截图显示两条 `111` 各自重复、`在干嘛` 也跟着重复，但 `?` / `干嘛` / `在` / `你刷什么呢` 都只有一条。

这个"只有用户消息翻倍"的不对称正是定位线索。查下来是**两个成因叠在一起**：

1. **重复写入（主因）**：`AgentTurnRunner.run` 在装配上下文前写了一遍用户消息，
   而 `SessionController.send()` 也写了一遍。同一句话进了两条库记录。
2. **认领不原子**：`flushTurn` 里 `pending.toList()` 与 `pending = mutableListOf()`
   之间没有临界区，真正的锁在**之后**才拿。防抖任务会被反复取消重启，
   于是两条路径能各自取到同一批消息 —— 既投给模型两次，也落盘两次。

修法：

- 明确约定 **用户消息由调用方落盘，执行器只负责读**（`AgentTurnRunner` 里那份删掉）
- 把"取批 + 清空"收进一个**非挂起**的原子操作 `claimPending()`，落盘在其后按不可变批次做一次
  （用 JVM `synchronized` 而不是 `Mutex`：`Mutex.lock` 会挂起并把续体丢回调度器，
  既让虚拟时间测试失效，也在应用里给重复认领留出窗口）
- 落盘时机从"按下发送"改到"认领"：界面新增 `ChatUiState.pendingItems` 专门显示
  还没进库的待处理气泡，否则会变成"点了发送没反应"

**顺带修掉的架构问题**：`SessionController` 原先直接依赖 `SoloChatApp` 与具体类 `RoomStore`，
因而**无法在纯 JVM 里构造** —— 这正是这个 bug 只能靠看截图发现的原因。现在它依赖
`TurnHost` / `StoragePort` / `EventSink` 三个接口，`SessionControllerTest` 用虚拟时间
覆盖防抖、落盘、插话、换会话四条路径。

而写这条测试的过程又抓出了上面第 1 个成因 —— 测试写完第一次跑就报
`expected:<[在吗]> but was:<[在吗, 在吗]>`，等于把用户看到的现象在 CI 里复现了一遍。

## 与方案的偏离（每处都有理由）

1. **加了第六种事件 `remember`**，并把记忆写入从"工具调用"改为"脚本里的一条事件"。
   理由：一轮一次调用的架构下，工具调用要多一次完整前缀往返（贵且慢），而记忆写入不需要返回值。
2. **联网搜索（原阶段 7 的一半）没做**。理由：它必然引入"模型要先声明意图、再二次调用"的往返，
   会破坏刚建立好的节奏与抢占模型。改到后面作为独立阶段做，届时按"两段式 + 正在查…提示"设计。
3. **场景摘要没做**。它是面对面模式长期可用的前提，但要先有真实使用数据才知道该在哪压。
   在它落地之前，长场景的上下文会持续变贵 —— 这是当前最大的已知欠账。
4. **不用 Robolectric**。它要在测试运行时下载 android-all，离线环境必然失败；需要 Context 的逻辑
   一律抽成纯函数再测（`ModelPricing` / `PricingRules` 就是这么拆的）。
5. **不做远程价格表**。QQ-agent 有"远程表覆盖内置表"的机制，但那要多一条网络依赖 + 缓存 + 失效策略；
   价格只影响展示的估算。用户想精确就填自填单价。

## 本机环境上踩过的坑（换机器会重新遇到）

1. **PowerShell 出不了网**：`curl` 报 `SEC_E_NO_CREDENTIALS`，`.NET HttpClient` 报
   `SSL connection could not be established`。**Node 的 https 正常**，所以下载统一走 Node
   （`tools/download-gradle.mjs`）。
2. **沙箱不允许写用户主目录**：`~/.gradle` 与 `~/.android` 都写不了。
   → `GRADLE_USER_HOME` 指到工作区内的 `.gradle-home`；**debug 签名密钥必须靠
   `ANDROID_PREFS_ROOT` 环境变量改位置**（`-Duser.home` 经 Gradle 守护进程会丢，实测无效）。
3. **命名管道被禁**：Kotlin/Gradle 守护进程之间靠它通信，导致
   `Could not connect to Kotlin compile daemon`。→ `gradle.properties` 里设
   `kotlin.compiler.execution.strategy=in-process`。
4. **JDK 只有 21**，而模块里声明 `jvmToolchain(17)` 会导致
   `Cannot find a Java installation ... languageVersion=17`。→ 改成"用当前 JDK、字节码目标 17"。
5. **`.bat` 必须纯 ASCII**：cmd 在中文 Windows 上按 GBK 解析，UTF-8 中文注释会吞掉换行。

以上多条的绕法都固化在 `tools/build.ps1` 里，日常构建直接跑 `构建.bat` 或
`pwsh tools/build.ps1` 即可。
