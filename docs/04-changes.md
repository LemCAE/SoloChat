## 2026-10-22 · 发送冲突：两条可复现并发路径

新增“助手历史写入挂起时插话不能丢掉已出口内容”和“手动重复推送遇到挂起标记仍只认领一批”两条定向用例，旧实现均失败。第一条复现：正常播出先把事件加入 writtenIds，再挂起写助手消息；插话取消该写入后，补写因 id 已认领而跳过，下一轮上下文缺少已出口的话。第二条复现：两个 push 都能在标记完成前读到同批代发。

修复为助手历史以不可取消小段与共享锁完成实际写入后再认领 id；插话收尾串联，下一轮等待旧轮取消与历史落定后才装配上下文。push 的读取/标记/起轮用提交锁串行，后到的重复 push 读到空批。先执行两条用例确认失败，再执行 SessionControllerTest 相关回归通过；本轮未重跑全仓测试，也未改真实旧记录。尚未将此修复包装/装机，用户观察到的偶发冲突不能全部归因于这两个窗口。

## 2026-10-08 · 历史里那些"被教坏"的轮次，不再原样喂回给模型

### 现象（用户原话：「现在解析好像正常了」）

解析确实好了：真机最新一轮 `事件数: 9 / 降级: false`，独立成条的停顿被折进下一条。
**但模型这一轮仍然写了 `{ "type": "typing_ms": 1600 }`** —— 提示词里那条"它不是一种事件类型"
的警告就在上面几行，它照写不误。为什么？

### 根因：上下文在教它自己

把那一轮的完整提示词拉下来数 `"type": "typing_ms"`：

| 出现位置 | 次数 |
|---|---|
| 提示词正文（我自己写的例子与警告） | 4 |
| **历史行** | **11** |

那 11 处是**模型自己以前几轮的输出**。链条是这样的：

1. 旧提示词写得含糊 → 模型把 `typing_ms` 当成一种事件写出来；
2. 那份输出 JSON 不合法 → 整段被降级成一条 `say` 落进**消息表**；
3. 消息表就是下一轮的**历史** → 模型读到自己上一次的输出，里面赫然写着这种写法；
4. 它把这当成"协议允许的写法"照抄 —— **错误一轮一轮复制自己**。

⚠️ 只改提示词治不了这个环：**范例比规则硬**，而范例在历史里，还一轮轮在增多。
而且历史现在**不设上限**（D10），这些 JSON 块永远不会自己滚出去。

### 改法（`PromptBuilder.renderHistory`）

助手历史里，只要是"整段 JSON"（以 `{` 开头且含 `"events"`）的那条消息，就**先喂给
解析器还原**，再按正常格式写进历史：

```
（窗台上两只杯子被天光照着）        ← scene
*陆昭把外套搭在椅背上*             ← act
睡吧                              ← say
```

- 还原用的是 `renderEventLine` —— 与正常落盘（`eventsToAssistantText`）**共用同一个函数**。
  两处写成两种格式，模型就会把动作当成台词，所以这一条必须只有一份实现。
- **救不回来的原样留着**（`degraded`）：那种情况我们也不知道它原本想说什么，
  编一份出来比留着更糟（D11）。
- 只动**模型看到的历史**，不动消息表、不动时间轴 —— 界面上那几轮的原始 JSON
  仍然是用户看到的样子，没有偷偷改写聊天记录。

### 证明

- 新增 3 条 `PromptBuilderTest`：还原成正常几行 / 救不回来原样留着 / 正常历史不被碰到。
- **红→绿**：把 `renderHistory` 里助手那行改回 `"[$stamp] 我：$text"` →

## 2026-10-08 · 模型输出解析：加一层"逐条抢救"，一个字符写坏不再赔掉整轮

### 现象（用户报的）

截图：面对面里角色回了一整屏**原始 JSON**，一条气泡，里面是完整的 `{"events":[…]}`。
用户的三条猜测都提了（`typing_ms` 是不是不能单独写、要不要放宽解析、特殊字符会不会出错），
并要一份"解析流程"的解释。

### 根因

那份输出里有一条 **`{ "type": "typing_ms": 2500 }`** —— 一个值后面**多了一个冒号**。
那不是合法 JSON（一个值的后面只可能是 `,` `}` `]`），于是 `kotlinx.serialization` 直接抛错，
`extractJson` 返回 null，`parse()` 走**降级**路径：把整段原文当成**一条 `say`** 发出去。
**其余 8 条事件全是好的，一起陪葬。**

### 取证（真机数据，不是推测）

用测试网关拉消息表（`/api/messages`，**界面投影看不出这件事**）：

| 会话 | 模式 | 消息数 | "原文是原始 JSON"的 assistant 消息 |
|---|---|---|---|
| 陆昭 `3f7a5d23…` | 面对面 | 216 | **27** |
| 小鲸鱼 `ac81b213…` | 聊天 | 91 | 0 |
| 新的对话 `f86ee8c5…` | 面对面 | 55 | 0 |

27 条集中在 **01:38–02:08 与 08:29–09:20** 两段。逐条抽查了两份（消息 id 999 / 1002），
坏点**都是同一个多余的冒号**，两份都在 `{ "type": "typing_ms": 1800/2500 }` 这一处：

```
{ "type": "typing_ms": 2500 },   ← 999 与 1002 都是这一处
```

修好之后把 **27 份原文全量**过了一遍（`tools/dump-degraded.ps1` → `RealOutputCorpusTest`）：

```
真机语料：27 份，仍降级 0，解析成空 0
每份救回来 8~12 条事件，各带 1~2 段折叠的留白，首条都是正常的 scene/act
```

也就是说 **27 条全是同一个形态**（独立成条的停顿 + 那个多余的冒号），不是多种杂症 ——
提示词里那一句话造成的，就在这一句话上收掉。

> 语料与工具都留着：语料在 `.tmp/degraded/`（不进版本库），
> 插上设备一条 `pwsh tools/dump-degraded.ps1` 就能重建，
> 之后 `:core:test` 会把它们逐条喂给解析器。**"跳过 ≠ 通过"**，见 02-handoff §4 第 9 条。

### 为什么模型会这么写（提示词的问题，不改代码也会继续出现）

`10-protocol-scene.txt` 旧文里写着：

```
- `typing_ms`：如果有停顿、犹豫、欲言又止的瞬间，用 `typing_ms` 表示这段沉默的长度（如 `2500`），
  它会渲染成一小段留白。
```

**没有给例子，也没说它挂在哪**。而上面的事件示例里只有 `scene` / `act` / `say`，
每一行都是 `{ "type": …}`。模型很自然地把它读成"一种事件类型"。
聊天模式那份协议里 `typing_ms` 是列在"**节奏字段**"小标题下的、紧挨着事件类型表，
所以那边 0 次出错 —— 差异就在这两份文件的写法上。

⚠️ 顺带记一笔：`act 1~5 / say 最多 8 句` 那批改动之后，面对面一轮的事件数从 2~4 条涨到 8~10 条，
`typing_ms` 的出现频率跟着涨 —— 提示词里这颗地雷是**在我自己的改动之后才被踩响的**。

### 改法

**① `ScriptParser` 从"一遍解析"改成四层**（从便宜到贵，顺序不能换）：

| 层 | 做什么 | 修的是 |
|---|---|---|
| 1 | 原样整份解析 | 正常输出（一个字符都不动） |
| 2 | **定向修补后**整份解析 | 多余的冒号、弯引号、单引号、全角标点、少逗号 |
| 3 | **原样逐条抢救** | 整份不合法时下钻，坏的那条跳过、好的照常 |
| 4 | 修补后逐条抢救 | 上面两种毛病同时出现 |

- 逐条抢救靠**大括号配对扫描**（认字符串与转义，所以正文里的 `{` 不会算错层级），
  规则是"能整体吃下就整体吃下，吃不下就下钻一层"。
- ⚠️ 扫描器收的是"**最外层配平区间**"，不是"第一个 `{` 到第一个 `}`"。截断的输出里
  外层大括号一辈子不闭合，里面完整的那几条仍然是候选 —— 半截的那条不播，但**不连累别人**。
- 修补走的是一个**逐字符状态机**（不是一串全局替换），因为字符串**里面**不能动：
  `"text":"他说“嗯”"` 里的中文引号是正文。弯引号刻意配成对（`“` 配 `”`），
  否则正文里的 `“` 会被当成收尾引号。
- `isLenient` 的边界实测过：它只放开"键和值可以不带引号"，**单引号一直不认**
  （旧注释写"单引号也见过"是错的，已改）。正文里的真换行、tab、控制字符它都认。

**② 独立成条的停顿认下来，折进下一条**（不新增存储类型、不改播放器）

模型把它当事件类型写，有两种形态都见过：`{"type":"typing_ms","ms":2500}`（合法 JSON）
与 `{"type":"typing_ms":2500}`（不合法）。意图完全明确，所以 `ScriptParser` 认下
`typing_ms` / `typing` / `pause` / `gap_ms` / `delay_ms` 这类"类型"，把毫秒数
折进**下一条**的 `typingHintMs`（停顿类）或 `gapHintMs`（间隔类）：

- 事件自己写的字段优先（模型在"这一条"上明确给了时长，别被前面那段概括的覆盖）；
- 没有数字的不当停顿（那更可能是别的自创类型，按未知类型丢掉更诚实）；
- ⚠️ 整轮**只有**一段停顿 → 当 `wait`（空脚本），**绝不降级**：
  降级正是"拿原始 JSON 占一个气泡"那个 bug 的样子。

**③ 提示词：说清它是字段，并给出写在里面的例子**

- `10-protocol-scene.txt`「节奏」整段重写：给出 `{"type":"act",…,"typing_ms":2500}` 这个例子，
  并明写"它不是一种事件类型"+ 写错的两种后果（留白丢 / 整轮废）。
- `10-protocol-chat.txt`「节奏字段」补同样的警告与例子。
- 两份协议的「输出格式」开头都加了一句"必须是合法 JSON，多一个冒号整份作废"。

### 刻意留的边界

**不猜"未转义的引号该在哪结束"**（`{"text":"他说"你好""}`）。那种只能靠猜，
猜错等于**替模型编内容** —— 比降级更糟。宁可让它明确坏掉（有测试守着这条）。

### 证明

- 新增 18 条 `ScriptParserTest` + 1 条语料测试（`RealOutputCorpusTest`），
  其中两条是**真机原文**（id 999 / 1002 逐字抄的），
  断言里的条数与留白时长都是照着原文数出来的（7 条 + 折叠的 2500/1800）。
- **红→绿**：临时把第 2~4 层摘掉（只留原样整份解析），跑同一批测试 →
  **9 条失败**（含两条真机原文）；装回去 → 全绿。
- **真机语料全量**：27 份"曾经降级"的原文，修完 **0 份降级**（见上）。
- `test` 全绿：**307 个**（core 229 + app 78，`--rerun-tasks` 之后从 XML 读的）。

### 还没做的

- 真机体感确认（新的解析层在真实输出上是否真的不再降级、折叠的留白观感对不对）。

我是指软件的UI界面里面的**」——
即：出厂人物卡与用户自己写的人设正文**不动**（那是内容，写谁就是谁），
要改的是**这一页给用户看的界面文案**。

### 改法

**① 第八段：`Persona.depiction`（怎么描写动作与景物）**

前一批已经把"素材"补齐了（`mannerisms` 动作库、`surroundings` 景物库），
但**素材不等于笔法**：同一条素材，有人该写得干燥短促，有人该写得黏稠多细节。
所以这一段的定义是"**写成什么样**"，与另外两处形成三层：

| 层 | 是什么 | 在哪 |
|---|---|---|
| 写什么 | 动作素材 / 景物素材 | `mannerisms` / `surroundings` |
| 写成什么样 | 偏听觉还是偏视觉、长短、用不用比喻、观察距离 | **`depiction`（新）** |
| 不许写成什么样 | 不写内心独白、不堆排比、不写成小说 | `20-style-scene.txt`（全局底线） |

与 `sceneVoice` / `surroundings` 一样**只在面对面注入**：在发消息模式里给模型笔法，
它就会开始写小作文。提示词里的段落顺序是「它身边的样子」→「怎么描写动作与景物」——
先拿到素材，再拿到笔法。

**② 界面文案去掉第三人称性别代词**

改动只在 `PersonaScreen`（以及 `PersonaDocument.template()` 的提示语）：
把"她的动作库""她紧张的时候""她待的地方"这类改成**省略主语**或「这个角色」。
同时把这条**写成了规矩**，避免下次又写回去：

- `PersonaScreen` 的类注释里写明这一页的文案不用第三人称性别代词；
- `02-handoff.md` §3 ⑧ 加了对应条目，§8 自检清单加了一条
  「动过面向用户的文案 → grep 一遍 `她`/`他`」。

⚠️ **别名表里的「她/他」必须留着**（`她身边的样子`、`只有她知道的事`、`她是谁`）：
那是"认出别人写的文档"的识别数据 —— 用别人的角色卡时，文档里写「她是谁」很常见，
认不出来才是 bug。`PersonaDocument` 的别名表旁加了注释说明这一点，
免得下一个人把它当成同一个问题扫掉。

**③ 数据库 v4 → v5：只加一列 `depiction`**

**为什么不把它折进 `MIGRATION_3_4`（v4 明明没上过真机）**：v4 的"没上真机"只是**我们这边**
的取证缺口，不代表 v4 没出去过 —— 带 v4 的 APK 已经交付，用户完全可能已经装上并写过数据。
折进去会让那台设备的库停在"版本 4、但没有这一列"，Room 打开时 schema 校验不过，
结果是**升级后直接打不开 App**。多一条迁移的成本只是一行注册，赌"用户没装过"的成本是打不开 App。

## 2026-10-08 · 人物卡扩成七段（含面对面素材）+ 小鲸鱼出厂卡 + 文件格式改成 JSON

### 需求

用户原话：「现在的人设提示词还是不够完善，尤其是我们这里还引入了"面对面"的模式，
那么景物描写/动作描写什么的都要用提示词约束/指导，而人物的习惯、语言（与聊天多少有点不一样）
也会有区别，还有这个人的习惯啊、动作什么的。这都是人设的一部分，而当前的提示词格式还是不够完善。
然后就是默认提示词把那个"小鲸鱼"也加上。」中途又加了一条：「导入文件的格式应该是 json 而不是 md」。

拆成四件事：

1. **人设字段不够用**。面对面模式的表达手段只有 `act`（动作）和 `scene`（环境），
   而人设里**没有任何素材** —— 只有「它是谁 / 怎么说话 / 关系与边界 / 只有你知道的事」四段文字。
   结果是模型每轮自己发明一个动作，表现是"这个人每轮都做不一样的小动作，不像一个人"。
2. **描写缺方法论**。`20-style-scene.txt` 当时只说了"动作比台词好""别多""把话头递回去"，
   **没教怎么写**：怎么把情绪翻译成动作、景物怎么服务气氛、什么算小说腔。
3. **要一张小鲸鱼出厂卡**。`assets/data/persona-templates.json` 里那张一直躺在仓库里、
   代码零引用 —— 旧版 `PersonaDefaults` 的 KDoc 还专门论证过"不要用它"（它是为 QQ 群写的）。
4. **导入格式改成 JSON**。Markdown 要认别名、标题层级、加粗、围栏，读错还只能靠一句告警兜着；
   JSON 的键名与字段一一对应，而且空字段也写出来，**文件自己就是文档**。

### 改法

**① 人设四段 → 七段**（`core/model/Conversation.kt` 的 `Persona`）：

| 新字段 | 管什么 | 注入时机 |
|---|---|---|
| `sceneVoice` 面对面时怎么说话 | 当面与打字的差别（更短更碎、靠动作） | **只在面对面** |
| `mannerisms` 习惯与小动作 | `act` 的动作库 | 两种模式都给 |
| `surroundings` 它身边的样子 | `scene` 的景物素材 | **只在面对面** |

**② 按模式注入**（`Persona.toPromptBlock(mode)`）：后两段只在面对面出现。
理由是它们是**描写素材** —— 在发消息模式里给模型一堆环境与"当面怎么说"的素材，
它就会开始写小作文，而"像在发微信"恰恰要求它别这么做。
`mannerisms` 两种模式都给：它是"这个人"的属性，不是某个模式专用的。

顺手钉住一条：**空段落不产生空标题**。留一个只有标题没有正文的段落，会让模型觉得
"这里应该有内容"于是自己编一段补上 —— 比不写更糟。而老卡上那三段一定是空的，很常触发。

**③ 描写的"怎么写"补进 `20-style-scene.txt`**（三节：动作怎么写 / 景物怎么写 / 台词与动作的配比）。
要点是几句能照着做的：写能被看见听见的东西、**不写内心独白**；具体到能画出来；
一个 `act` 只做一件事；**动作从人物卡的「习惯与小动作」里来，反复用那几个**；
一次只给一个感官焦点；景物跟着情绪走；不堆比喻排比通感、不总结；
台词与动作交替、**嘴硬的时候台词和动作要相反**。

同时 `20-style-chat.txt` 补一节「动作（聊天里少用，但用对了很值）」，把 `mannerisms`
在聊天模式的用法也接上。⚠️ **两处都没写任何"N 条"** —— 遵守上一批定下的
「条数上限只在 `10-protocol-*.txt` 里写」那条维护约定。

**④ 小鲸鱼出厂卡**（`PersonaDefaults.xiaojingyu`）。**改写，不是原样搬**：
保留的是这个角色本身（身份、蓝发鲸鱼尾的形象、傲娇嘴硬心软、雷点"蓝色大肥鱼"、
偷吃 token 等梗、"用户"这个彩蛋称呼、以及整份 AI 味黑名单），
去掉的是**平台机制**（群聊铁律、被 @ 必回、拍一拍、表情包库、引用某群友，
以及 `send_message` / `web_search` / `list_stickers` / `memory_append` 这些这个 App 根本没有的工具名）。

顺带两处：`PersonaDefaults.builtins()` 一次给两张；**种子逻辑从"列表为空才种"
改成"按 id 逐个补"** —— 这样老用户升级后会自动多出小鲸鱼，而改过的卡不会被覆盖。

**⑤ 文件格式改成 JSON**（`PersonaDocument`）：新增 `toJson` / `FormatID` / `FormatVersion`，
`template()` 也改成 JSON（**由 `toJson` 生成**，不手写字符串 —— 手写的话将来加字段忘了改模板，
用户复制到的就是一份缺字段的模板，而那种错误只有导入时才暴露）。
导出按钮改成导出 JSON。**Markdown 仍然读得进来**（老文件与"顺手粘一段"的退路），
但不再是格式。`parseJson` 还会认文件头：`format` 不对、`version` 比 App 新，都只给一句告警而不拒绝。

**⑥ 数据库 v3 → v4**（`MIGRATION_3_4`）：三条 `ALTER TABLE persona ADD COLUMN ... NOT NULL DEFAULT ''`。
**一个字符的用户数据都不动**（对比 `MIGRATION_2_3` 那条要 UPDATE）。老卡上这三段是空串，
语义是"这个人没写这一段"。

## 2026-10-07 · 发送方式：加一个开关，可切"自动防抖"与"手动两段"

### 需求

用户提出：按下发送**先只把消息放进对话里**（时间线可见、但不发给模型），**再按一次**才推给模型。
字空但有代发时发送键变蓝；有字时是原来的样子（"白"）；都没有时是灰的。

要求是**不动现有的防抖机制**，只加一个开关在两种模式间切 —— 所以两种模式共用同一套流水线
（防抖判定、认领、落盘、回合、播出全都没改），唯一的分歧是"**什么时候把那批消息交给模型**"。

| 模式 | 按下发送 | 那个动作 |
|---|---|---|
| **自动（防抖）**（默认，原来的行为） | 进内存待处理队列 → 重启防抖定时器 → 到点自动开工 | 用户不用管 |
| **手动（两段）** | 只落进时间线（"代发"） | **再按一次**才推给模型 |

### 代发消息存在哪：以**数据库**为准，不是内存

自动模式下 `send()` **刻意不落盘**（注释写明了原因：防抖窗口只有几秒，"这几秒里进程被杀"
是唯一会丢的情况，用"显示两遍"换它不值得）。**手动模式把那个前提推翻了** ——
窗口变成"随便多久"，于是切会话（`open()` 会清内存队列）、离开聊天页（`close()`）、
进程被杀，**代发的消息全会没**，而界面上明明显示过。

所以手动模式的代发**必须落库**。做法是复用 `Message.sentToModel` —— 它在此之前是个**死字段**
（全仓库只有两处写死 `false`，唯一读它的是调试接口 `/api/messages`，注释还是错的），
用它就**不用做数据库迁移**：

- 按下发送 → 立刻写一条 `role=user, sentToModel=false` 的消息 → 它就是时间线里一条正常气泡
  （单一数据源，因此也不会出现"同一条画两遍"那个老 bug）
- **模型上下文排除未推送的用户消息**：新增 `StoragePort.modelVisibleMessages`，
  SQL 是 `AND (role != 'user' OR sentToModel = 1)`。
  ⚠️ `role != 'user'` 那一支不能省 —— assistant/system 的 `sentToModel` 恒为 0，
  只按 `= 1` 过滤会把模型自己说过的话**全部滤掉**，正是文档里记过的那个
  "模型看不到自己说过的话"。
- 再按一次 → 标记 `sentToModel = true` + 起一轮（`startTurn` 的约定正是"调用方负责落盘"，
  这里**不落盘**：它们已经在库里了，再写一遍就是"用户消息成对出现"）
- 刻意**不做成** `recentMessages(..., forModel = true)` 这种布尔默认参数：
  默认值给错方向，泄漏是静默的（同样的教训见 `listMemories` 的 `null` = 全部）。
  两个方法各有各的名字，调用点自解释。

### 交付时自己踩到的一个坑（值得记）

自动模式的落盘走的是既有的 `persist()`，而那里 `Message(...)` **没写 `sentToModel`** ——
默认 `false`。加上"上下文排除未推送"之后，这会让**自动模式下用户说的话永远进不了上下文**：
不报错、气泡照旧显示、模型却看不见。**加过滤的那一刻，必须同时把所有"这条消息已经交给模型了"
的写入点一起标上。** 已在 `persist()` 里显式写 `sentToModel = true` 并注明原因。

### 按钮三态

| 输入框有字 | 有代发 | 样子 | 按下去 |
|---|---|---|---|
| 是 | — | 亮图标（原来的样子） | 把这几格送进时间线 |
| 否 | 是 | **图标染成主题色**（仅手动模式） | 推给模型 |
| 否 | 否 | 灰、不可点 | 没事可干 |

**"有字"优先**：手上有字就一定是"再发一条"而不是"推送" —— 这样同一颗键的行为才可预测
（发完手上就空了，自然落到蓝色那一态）。无障碍文案也跟着变：
蓝色时读作"推送 N 条待发消息给模型"。

⚠️ **只改图标染色，不加背景色**（用户明确要求）。这一页（以及整个 App）的按钮语言是
"同一个图标，靠染色/透明度表达状态"：禁用态由 `IconButton` 自己降透明度，所以三态是
**亮 / 主题色 / 灰**，形状始终不变。第一版加了个实心圆底，被否掉了 ——
那会让它突然变成一个"主要按钮"，和旁边的输入框、上面的标题栏打架。

### 打断时机：推送时才打断

自动模式里"用户一发消息"就等于插话打断（停播、未播的取消）。手动模式下触发点**移到推送** ——
语义是"我说出来了"才打断。第一次按下不打断：那时用户还没决定要说，角色可以继续说，
界面上的观感就是聊天软件里"它还在说，我的话在下面等着"。

### 切回自动模式会补推

手动模式留下的代发，如果用户把开关切回自动：`open()` 时会**补推一次**。
不补这一步是个死局 —— 那些消息永远躺在库里，而自动模式又不画"蓝"，用户没有任何提示，
只会觉得"我明明发过那句话"。只在这一处补，且用 `turnJob?.isActive != true` 挡住在跑的回合。

### 取证

- 全量测试 **276 个全绿**（core 200 + app 76），0 警告。本批新增 6 条：
  第一次按下不起轮（`llm.calls == 0` 且消息已落盘、`pendingSendCount == 1`、`pendingItems` 为空）、
  第二次按下起轮且推完归零（并断言推出去的内容**真的**进了上下文）、
  **代发不进上下文（引擎自己起的那轮也看不见）**、自动模式行为与从前一致、
  手动留下代发后切回自动会被发出去、
  **推送成功立刻不蓝**（见下面那条真机 bug）。
- **红 → 绿**：把 `AgentTurnRunner` 里那句 `modelVisibleMessages` 临时换回 `recentMessages`
  → 泄漏测试 **FAILED**（`AssertionError at SessionControllerTest.kt:700`）→ 换回来全绿。
  这条不变式（"不按第二次就不发给模型"）值得这样钉一次。
- 假存储 `FakeStore` 同步**照抄 SQL 语义**实现 `modelVisibleMessages` / `unpushedUserMessages` /
  `markUserMessagesPushed`：真机上那条 SQL 在纯 JVM 里跑不了，复刻错了测试会替真机
  "证明"一个不存在的行为。

### 真机反馈修掉的一个 bug：蓝色按钮要点两次才变灰

用户实测："蓝色按钮要点 2 次才变灰，虽然一次就会发送，对话完成也会自动变灰。"

三个现象一个根因：`pushUnpushed` 里标完数据库**没刷新界面状态**，`pendingSendCount` 一直停在 1。

- 第一次按下：消息**确实推出去了**（`markUserMessagesPushed` + `startTurn` 都干了），
  但界面不知道 → 图标保持蓝；
- 第二次按下：`unpushedUserMessages` 已经是 0 条 → 走"空列表只刷新界面"那条分支 →
  **这时才变灰**（这一次其实什么都没发）；
- 回合收尾那次 `reload()` 也会把它纠正成 0 → "对话完成也会自动变灰"。

修法：标记完立刻 `copy(pendingSendCount = 0)`。"推送成功"必须是它变灰的触发点。

**这条 bug 暴露了一个测试盲区**：原来的 `推完归零` 那条是等整轮跑完才断言的，
而收尾的 `reload()` 会顺手把状态修好 —— 所以**它对这个问题是假绿的**。
新测试必须在"请求已发出、回合还没结束"这个瞬间取状态，于是给 `StubLlm` 加了一个
`onRequest` 同步回调（和 `FakeStore.onDelivered` 同一个道理：`advanceUntilIdle()`
一次跑完整轮，从外面轮询永远抓不到中间那一帧）。
**红 → 绿 验过**：去掉那行刷新 → `AssertionError at SessionControllerTest.kt:714` → 加回来全绿。

### 【必须做的】第二条数据库迁移 v2 → v3（把那个死字段的老数据标对）

**这一条是交付时自己发现的，性质与上面那个 `persist()` 的坑同源，但后果更严重。**

`sentToModel` 以前是死字段 → **库里所有历史用户消息都是 `false`**。一旦启用过滤，
它们全会被当成"代发"：

1. 模型上下文里**看不见用户以前说过的任何话**（只剩角色自己的发言）；
2. 切回自动模式时那句"补推"，会把**整场老会话的用户消息**当成代发 ——
   一打开会话就凭空起一轮，每打开一次花一次钱、多一段角色自说自话。

`MIGRATION_2_3` 就一句：`UPDATE message SET sentToModel = 1 WHERE role = 'user'`。
这就是**事实** —— 这个字段启用之前，`recentMessages` 一视同仁地把它们全喂给了模型。
只动 `user`：assistant / system 本来就该是 0（过滤条件是 `role != 'user' OR sentToModel = 1`）。

**为什么不做成 App 启动时的一次性修补**（那样更省事，也不用碰 schema）：那样有一个窗口 ——
DB 已经打开、修补还没跑完，而用户已经点进某个会话，上面第 2 条事故就发生在窗口里。
迁移在 **DB 第一次打开、任何查询之前**跑完，没有窗口。

### 取证（续）

- **迁移离线拿真机数据跑过**：迁移前 98 条用户消息**全部** `sentToModel=0`（这正是不迁移的后果），
  跑完 98 条全变 1、assistant 234 / system 3 一个字没动、总条数不变、`integrity_check = ok`、
  模型可见查询把整场会话一条不漏地取回来。
- **迁移在真机上也验过**：装包冷启后拉库 → `user_version = 3`、integrity ok、
  用户消息 **132 条全部 `sentToModel=1`**、**未推送 0 条**、陆昭那场 348 条 → 模型可见 348 条
  （没有任何东西被藏起来）。
- 启动日志无 ERROR/WARN、无异常；`usage` 表显示最后一次调用停在这之前的 23:49 ——
  也就是说带 bug 的那一版（装上去到装回修好版之间有几分钟）**没有触发任何一轮**，
  用户数据没有被那两条事故碰到。
- 待用户验证：切到"手动（两段）"，发一条看它是否只进时间线且发送键变蓝；再按一次看是否起轮；
  中间切一次会话/退到列表再回来，看代发还在不在。

### 没做 / 待观察

- **没有"自动兜底计时"**（纯手动）。讨论过"5 秒不按就自动推"的变体，用户选了纯手动；
  真要加，实现上只差一个计时分支。
- 界面**没有文字提示**"还有 N 条没推"（只有蓝色按钮）。曾考虑复用 `pendingHint` 那一行，
  但那一行在本轮之前已经因为"每轮闪两次"被撤掉了（见 `ChatScreen` 里的注释），
  所以先不加，等真觉得不够醒目再说。
- 推送时如果同一条用户消息**已经被别的路径标记**过（并发两处 push），靠 `markUserMessagesPushed`
  的 `IN (:ids)` 幂等 —— 但并发 push 本身没有互斥，属于"要点两下才可能发生"，先不设防。

## 2026-10-07 · 编辑人物卡时也能导入文档（"改这张卡"而不是"再建一张"）

### 缺的是哪一半

人物卡页**一直有导入**（右上角 →「导入文档…」），但它和编辑是两件事：

| 入口 | 行为 |
|---|---|
| 列表页「导入文档」 | **建新卡**：`PersonaImporter.toPersonas` 每次发新 id，注释里写明了这是刻意的 —— "导入是一件用户预期只增不改的操作" |
| 编辑页 | 只有 6 个输入框 + 保存。**要更新一张已有的卡，只能手敲或粘贴** |

于是真实需求落在这里：**手上有一份改好的文档，要把这张卡换成它**。

### 改法

- **core 新增纯函数 `PersonaDraft.applyTo(base)`**（放 `PersonaDocument.kt`，和 `toPersona` / `toDraft` 一起）：

  ```kotlin
  fun PersonaDraft.applyTo(base: Persona): Persona = base.copy(
      name = name.ifBlank { base.name },
      tagline = tagline.ifBlank { base.tagline },
      avatar = avatar.ifBlank { base.avatar },
      identity = identity.ifBlank { base.identity },
      ...
  )
  ```

  两条语义是刻意定的：

  1. **保留本地事实**：`id` / `builtin` / `createdAt` 一个字不动（`builtin` 两个方向都不能变 ——
     导入不能把普通卡变成删不掉的出厂卡，也不能反过来）。`updatedAt` 留给保存那一层打点。
  2. **空段落 = "文档里没写这一段"，不是"清空"。** 只有文档不完整时两种语义才有区别，
     而那正是最容易出事的时刻：一份只写了「怎么说话」的文档，用"清空"语义会**静默删掉**
     用户手敲的另外三段，删完还看不出是导入干的。符合本项目一贯的取舍
     （见 D10 的"宁可多看一条，也不要让用户发现东西凭空少了"）。

- **编辑页顶栏加「导入」**（和「保存」并排）+ **导入预览对话框**。
  预览必须**逐段列出"这次会替换哪几段"** —— 因为空段落不覆盖，用户得看得见哪几段**不会**被换，
  否则"为什么这段还是旧的"就成了一个没有答案的问题。
  点确认只**填进编辑框**，不落库；用户检查后自己点保存。

- 复用了列表页那整套读文档的胶水（`PersonaImporter.read/parse/displayName`：
  宽 MIME、UTF-8、256KB 上限、失败抛异常），**没有新增任何 Android 侧读取代码**。

### 顺手处理的两个边界

- **文档里有多张卡**：编辑语境下只能用一张，所以只取第一张，并在预览里用醒目颜色写明
  "这份文档里有 N 张卡，只会用第一张（想全部导进来请回列表页）"。
  不写这句的话，用户会以为四张合并进来了。
- **文档里只有名字**：`PersonaDraft.hasContent` **刻意把"只有名字"算作没内容**
  （建新卡时它防的是"导入成功一张空卡"）。这个分支要**说清是哪一种**：
  "只有名字「X」，四段人设都是空的 —— 填进去等于什么都没变"，
  而不是笼统的"没有可用的内容" —— 否则用户看着文档里明明有名字会莫名其妙。

### 取证

- 全量测试 **全绿**，0 警告。新增 5 条
  （`PersonaDraftApplyTest`）：四段都写→全替换且保留本地事实、**空段落保留原文而不是清空**、
  空草稿原样返回、只有名字只换名字、**出厂标记两个方向都不改**。
  最后两条是"防写反"的：写反了只会在一半情况下出错，只测一个方向发现不了。
  ⚠️ 这一节原来写的是"251 个全绿（core 187 + app 64）" —— 那个数字**偏小**，
  原因见 [02-handoff.md](02-handoff.md) §5 的「别拿 test-results 里的 XML 数测试」。**
- 待用户验证：在编辑页点「导入」，选一份文档，看预览列的"会替换"与"名字"是否符合预期，
  确认后编辑框被填上、但**没有**直接落库。
- **用户已在真机上验证：正常。**

### 没做（可选，没提需求就不加）

编辑页里没有「格式说明与模板」入口（只有列表页有）。要在编辑页看模板得先返回列表页。
真觉得别扭的话，把那个对话框的入口一并挂到编辑页顶栏即可，改动很小。

## 2026-10-07 · 条数上限：三处数字打架 → 收成一处；面对面放宽，并加"把话头递回去"

### 现状核对：条数限制**全在提示词里，代码零上限**

`ScriptParser` 只夹时间值（`gap_ms` / `typing_ms`），**事件条数一条都不丢**，
`Player` 也照单全播。所以放宽条数是纯提示词改动 —— 但先要解决数字本身在打架：

| 位置 | 改之前说的是 |
|---|---|
| `10-protocol-chat.txt` | 普通回话 1 条，**最多 4 条**（同一段又写"4 及以上条"，自己跟自己矛盾） |
| `20-style-chat.txt` | 默认 1 条，**最多 2 条** |
| `10-protocol-scene.txt` | 一轮 **1~4 个事件**（事件含 `act`/`scene`，不等于"几句台词"） |
| `20-style-scene.txt` | 环境"**最多一到两句**"，台词没有数字 |

四条里有三条互相矛盾，而且**它们全在同一个稳定前缀里** —— 模型同时读到"最多 4 条"
和"最多 2 条"，谁赢没人知道。

### 改法：数字只写一处，风格文件改成指路

- **协议文件（`10-protocol-*`）拥有数字** —— 那是"格式/硬限制"该在的地方。
- **风格文件（`20-style-*`）不再写任何条数**，改成"上限见上面「输出格式」那一节"，
  自己只保留定性的约束（单条 ≤30 字、不要小作文、环境别多）。
  这样以后调数字只会改一个地方 —— 这次的矛盾就是"同一个数写在两个文件里"造成的。
- 两处都补上同一句：**上限不是任务量**（默认就回 1 条；能一句说完就一句）。

**新的数字**（用户定的）：

| 模式 | 上限 |
|---|---|
| 聊天 | 普通回话 1 条，**最多 4 条**（统一到 4；讲故事/一口气吐槽才会到 4） |
| 面对面 | 动作 `act` **1~5 个**（必要时可以更多，但别记流水账）、台词 `say` **最多 8 句**、环境 `scene` **最多 1 句** |

### 同时加的行为约束："抢着不让对方说"

用户反馈的另一个现象：面对面时偶尔会**一轮把自己的话全说完**（"一直在逗人家"），
对方只剩下"嗯"可以回。这与"放宽条数"看似矛盾，其实是**两个不同的量**：

- **放宽的是"量"**（能说多少）；
- **收紧的是"收尾"**（最后一条要不要把话头递回去）。

所以在**风格文件**（"观感"该管的地方）加了三条：

- **最后一条把话头递回去**：用一个动作、一句没说完的话、或者一个真的在等对方回答的问句收尾；
- **不要自问自答**，也别在同一轮里替对方把反应写好；
- 把动机写明白："你会想逗对方、会想一口气把好玩的事都讲完 —— 这是好事，
  但**每轮都要留一个口子给对方**。抢着说满，对方就只剩下「嗯」可以回了。"

### 代价（先说清，免得以后当成 bug）

面对面一轮**用满**是 `act 5 + say 8 + scene 1 = 14 个事件`。场景节奏是每条
`sceneBeatMs`（默认 700ms）起，所以极端情况一轮要播 **12~15 秒**。
插话随时能打断（未播的直接取消），所以这是可接受的；但如果以后觉得"演太久"，
**第一个该动的是节奏页里的 `sceneBeatMs`，而不是把上限改回去** —— 上限放宽的价值
在于"需要时能说够"，不在于"每轮都用满"。

### 取证

- 改的全是 `assets/prompts/*.txt`：**不进任何测试的输入路径**（测试用的是内联的
  `PromptResources` 字符串，没有测试读 assets）。所以这一批没有可跑的断言，
  **唯一有效的取证是用户在真机上的观感**：面对面是不是更丰富了、是不是每轮留了口子、
  聊天是不是没变成刷屏。
- 顺带的一次性成本：稳定前缀的字节变了 → 服务商侧缓存**失效一次**，之后重新稳定。
- 待用户验证。

**维护约定（重要）**：条数上限**只在 `10-protocol-*.txt` 里写**。
以后要调数字，改那一处；风格文件里出现任何"N 条"都算回归。

## 2026-10-07 · 面对面里仍弹"看起来你们要见面了" —— 判定写了，但没有生效

### 机理：过滤只用在"写日志"上，抛出去的是没过滤的值

`AgentTurnRunner` 里本来就有这句判断：

```kotlin
val proposal = if (config.allowModeSwitch) script.nextMode else null
if (proposal != null && proposal != conversation.mode) { /* 写一条【模式提议】事件 */ }
emit(AgentScriptReady(modeProposal = proposal, ...))   // ← 用的是没过滤的那个
```

于是：**提议"切到已经在的模式"照样被抛到界面**，`ChatScreen` 弹出一张
"看起来你们要见面了"的卡片 —— 而你们本来就面对面。

**这个 bug 在数据里查不到**，这是它最阴的一点：因为那句判断把**日志事件**挡掉了，
库里既没有提议事件、也没有多余的消息，事件时间线完全干净 —— 只有界面上多一张卡片。
（真机库核对过：库里 3 条 `【模式提议】` 全是 `chat → scene` 的**合理**提议，
按构造就不可能留下"同模式提议"的痕迹。）

### 改法：判定只留一处

```kotlin
val proposed = if (config.allowModeSwitch) script.nextMode else null
val proposal = proposed?.takeIf { it != conversation.mode }   // ← 同一处判断，两个用途
if (proposed != null && proposal == null) Log.info(TAG, "模式提议「…」与当前模式（…）相同，已忽略：不弹卡片")
```

- **界面层不兜第二遍。** 同一件事有两个判定，以后改坏其中一个不会有人发现
  （见 [02-handoff.md](02-handoff.md) §3 ③）。

## 2026-10-07 · 历史注入改成"全量"（暂时放开条数上限）

### 起因：那个 40 是按"一轮一行"挑的，语义早就偏了

查上下文注入链路时数出五道闸，全是**条数 / 字符**级的硬切，一处 token 预算都没有：

| 环节 | 上限 | 位置 |
|---|---|---|
| 稳定前缀（安全 + 人物卡 + 协议 + 风格 + 记忆规则） | 无 | `PromptBuilder.build` |
| 最近历史 | **40 条**（4~200） | `ChatConfig.historyLimit` |
| 记忆 | 24 条 + 2000 字符 | `AgentTurnRunner.pickMemories`、`MEMORY_BUDGET_CHARS` |
| 场景摘要 | 3 条 | `takeLast(3)` |
| 被打断提示 | 3 条 | `takeLast(3)` |

要命的是历史的单位是**气泡**（`message` 表一行 = 一个气泡），而面对面模式一轮
通常占 4~6 行（说三句 + 两个动作）—— 40 条实际只够 **4~6 轮**。
这个默认值是按"一轮 = 一行"的旧语义定的，**"一个气泡一条消息"上线后它的有效窗口
缩到了原来的三分之一**，而设置页上还写着"默认 40"。

证据（真机那份库，两场真实会话）：

| 会话 | 消息总数 | 全量字符量 | 最后 40 条 | 被丢掉 |
|---|---|---|---|---|
| 陆昭（面对面） | 153 | ≈ 4496 | ≈ 1175 | 113 条 |
| 新的对话（面对面） | 129 | ≈ 4277 | ≈ 1337 | 89 条 |

也就是说模型当时只看得到这场对话的 **四分之一**。

### 决定：现在不在这里省

稳定前缀（安全 537 + 协议 1772 + 风格 997 + 记忆 626，再加人物卡）本身就约 4000 字符，
而**全部历史也才 4500 字符** —— 掐历史省下的那点 token，远不如"模型记得住"值钱。

所以：**暂时放开，不做按轮切。** 以后加上下文压缩时再换掉这个旋钮，那时的口径是
"近 N 轮原文 + 更早的压到预算 token 以内"，**按 token 掐，不按轮掐**。

### 改了什么

- `ChatConfig.historyLimit` 默认 **0 = 不限**，并新增 `historyWindow`：把 0/负数
  **翻译成 `LIMIT -1`**。
  **为什么要专门有个翻译**：SQLite 里 `LIMIT 0` 是"一条都不要"、`LIMIT -1` 是"全都要"，
  两个只差一个字面量的取值，差别是整个上下文 —— 而且错掉时**没有任何症状**
  （界面正常、日志正常，只是模型失忆）。所以这个翻译只留一处，Room 层原样透传，
  `Ports.recentMessages` 的注释里写明了"实现不能把它原样拼进 SQL"。
- `SettingsStore`：`Snapshot` 默认值 0，`setHistoryLimit` 的夹取从 `4..200` 放宽到 `0..100000`。
- 设置页文案：`0 = 不限（默认）`，并写明单位是"条 = 气泡数，面对面一轮占 4~6 条"。
- `AgentTurnRunner` 里"丢掉与上一轮完全相同的 say"那处的比较窗口 **12 → 60 行**：
  同样因为一轮占 4~6 行，12 行有可能整个都是本轮的，于是"上一轮"找不到、
  `?: return events` 静默跳过去重 —— 表现只是"偶尔又重复了一句"，看不出是窗口太小。

### 【必须做的】旧值 40 的一次性迁移

**光改默认值对已经跑过的机器无效。** 真机上拉出来的 DataStore 里
`history_limit = 40` 是**明确存着的**：设置页的保存是**整页写**，只要在接口页点过一次
保存，40 就被当成"用户的选择"落了盘。不迁移的话，这次改动对这台机器完全没效果，
而界面上还显示着 40，看起来像"改了没用"。

`SettingsStore.migrateLegacyHistoryLimit()`：一次性、幂等（打
`history_limit_migrated_v1` 标记），**只认恰好等于旧默认值 40 的那一种取值**，
别的取值一律尊重原样；迁移后用户再手动填 40 就是真的要 40。
调用点在 `SoloChatApp.refreshConfig()` 里、**读快照之前**（否则读到的还是旧值）。

### 取证

- 全量测试 **244 个全绿**（core 182 + app 62），0 警告。本批新增 5 条：
  `ChatConfigTest` 4 条（默认=不限、显式条数透传、负数当不限、
  **"不限绝不能翻成 0"**）、`PromptBuilderTest` 1 条（给 200 条历史，一条不少地进提示词，
  钉"某处悄悄加个 `take(N)`"这种失败）。
- `SessionControllerTest` 的假存储跟着改成**照抄 SQL 语义**（`limit ≤ 0` = 不限）：
  它原来是 `takeLast(limit)`，而默认值现在是 `-1` —— 假存储比真实现严格，
  就会把"默认全量注入"错报成崩溃。
- **真机数据**：上面那张对比表（153/129 条、4496/1175 字符）是用 `adb exec-out` 把
  `solochat.db` + `-wal` 拉下来、用 Python 的 `sqlite3` 直接算的，不是估的。
- **`LIMIT -1` 那条 SQL 拿真数据跑过**（Room 生成的语句没法在纯 JVM 里测，
  而它正是整条链路上唯一测不到的一环）：同一句
  `SELECT * FROM message WHERE conversationId=? ORDER BY id DESC LIMIT ?`，
  参数 `-1` → **153 条（全部）**、`40` → 40 条、**`0` → 0 条**。
  最后那一行就是"0 直接下去"的后果：上下文整个空掉，而且不报任何错。
- **旧值迁移在真机上验过**：装包并冷启一次后把 DataStore 拉回来解出来 ——
  `history_limit` 从 **40 变成 0**，`history_limit_migrated_v1 = true`。
  （迁移前特意先确认过库里存的就是 40，所以"光改默认值"确实会无效。）
- 待用户验证：装新包后发一条消息，看会话详情里的历史构成（"我 N 条"）是否明显变大。
- **用户已确认：上下文现在是正常全量注入的。**

### 已知没做（都是独立决定，不在这一批里）

- **老会话里 assistant 行是"一轮一行合并"写的**：`f86ee8c5` 那场 16 行里 14 行是多行合并
  （`'喵？\n我才不笨 老大才笨'`），是"一个气泡一条消息"上线之前的格式。
  内容没丢，但第二行起没有 `我：` 和时间戳前缀，读起来像同一个气泡里的换行。
  要拆开就得**改写用户真实的历史行**，代价和风险都不小，暂时不动。
- **有 2 个轮次共 4 行从未落盘**（事件表里是 `DELIVERED`，消息表里没有）：
  模型永远看不到那 4 行。可从 `event` 表回填，但那要新增一条"修复历史"的迁移，
  单独评估。**注意这不是本次改动引入的** —— 是当年那个"写助手历史的代码从来没执行过"
  的残留。
- **变动区的位置**（记忆 / 当前模式 / 刚被打断 / cue 在历史**之前**）：实测两轮连续提示词的
  共同前缀已经 **97.1%**，所以挪到历史之后**在常态下一分钱不省**；它的价值是
  "变动区一变就清掉后面 5042 字符历史"这个塌方，以及**压缩落地时不自相抵消**。
  已按 D10 决定**与上下文压缩一起做**，现在不动。目标形状也在 D10 里定下来了：
  **摘要放最前（时间顺序）+ 变动区放最后**，中间是只追加的原文。
  实测数据与理由都记在 [01-decisions.md](01-decisions.md) D10 里。
- 记忆的字符预算用的是 `break` 而不是 `continue`：一条超长记忆会把它后面**所有**
  记忆一起丢掉（排序是置顶优先，所以一条长的置顶记忆可以静默清空其余全部）。
- `PromptContext.spokenEvents` 已是**死参数**（`PromptBuilder` 里从头到尾没读过它，
  历史只从 `message` 表来），但 `AgentTurnRunner` 仍每轮 `eventsOf(conversationId)`
  把该会话全部事件读出来（无 limit）只为算 `interruptedNote`。

## 2026-10-07 · 节奏参数全部进设置、设置页分层、记忆按人设分开（**第一条数据库迁移**）

### ① 节奏参数做成"一张表"

原来设置页只能改 4 个节奏参数（每字最少/最多、打字每字、"愣一下"封顶），
而 `PacingConfig` 里有 20 个 —— 其余 16 个（含刚加的面对面那一组）**只能改代码**。

现在 `core/protocol/PacingParams.kt` 是一张表：每个参数带 `key / label / hint /
default / min / max / group` 和 `read / write` 两个映射。

**为什么非要做成表**：20 个参数如果逐个手写"键名 + 默认值 + 上下限 + 读 + 写"，
加一个参数要改**五个地方**，漏一处就是 **"设置里改了没生效"** ——
它不报错、不崩，只是那个数字永远是默认值。一张表只有一处。

表由 `PacingParamsTest`（8 条）钉住三条不变式：

1. **表覆盖 `PacingConfig` 的每一个字段**（用反射数 `declaredFields`）——
   以后加了字段忘了进表，测试立刻红。
2. **表里的默认值 == `PacingConfig()` 的默认值** —— 否则设置页显示一个
   程序根本不用的数字，用户会以为改了没生效。
3. 键名唯一、`min ≤ default ≤ max`、读写闭合、写一个不误伤别的。

`SettingsStore` 相应改成 `setPacingParam(param, value)` + `Snapshot.pacing: PacingConfig`
（整包构造，由表 fold 出来），`SoloChatApp.refreshRhythm()` 变成一句
`pacingConfig = snapshot.pacing` —— 不再逐个字段搬运。

### ② 设置页分层

`SettingsScreen` 拆成「主菜单 + 子页面」：接口与模型 / 节奏 / 价格与成本 / 行为 / 排查。
子页面用**文件内的状态**（`SettingsPage` 枚举）而不是导航路由：这几个页面本来就不需要
深链接，加路由只是多一层 plumb。**但配了 `BackHandler`** —— 否则系统返回键会把整个
设置页弹掉，而不是回上一层。

顺带补上了 `priceCached`（缓存命中单价）的入口 —— 它一直是"有存储没界面"。

### ③ 记忆按人设分开（`personaId`，空 = 通用）

不同人设是不同的人。共用一份记忆会让「小默」知道只有跟「阿岩」聊过的事 ——
这是这个 App 里最容易破坏沉浸感的错，而且用户很难指出哪里不对。

- `Memory.personaId`，**空串 = 通用**（哪张人设都能看到）。
- 过滤语义（"自己的 + 通用的"）放在**存储层** `listMemories(personaId)`：
  `null` = 全部（管理页用）。放在一处就不会有人漏 —— 注入时传了 `null` 就等于串味。
- 注入侧 `AgentTurnRunner.pickMemories(persona.id)`；写入侧用
  `ChatUiState.personaId`，那是 **`resolvePersona` 解析之后生效的** id，不是会话上存的
  原始值（原始值可能为空、可能指向已删的卡）—— 用错就会"记了但从来不出现"。
- 去重也只在**同一张人设**范围内做：不同人设完全可以各记一条同样的内容。
- 记忆页新增：顶部归属筛选（全部 / 通用 / 各人设，带条数）、每条卡片上的归属、
  手动加/改时可以选"给谁看"。人设被删掉后显示"（已删除的人设）"而不是假装通用。

### ④ 【第一次】数据库迁移 v1 → v2

`Migrations.kt` 里 `MIGRATION_1_2`：

```sql
ALTER TABLE memory ADD COLUMN personaId TEXT NOT NULL DEFAULT '';
UPDATE memory SET personaId = (SELECT personaId FROM conversation
                               WHERE conversation.id = memory.sourceConversationId)
 WHERE sourceConversationId != '' AND EXISTS (...);
```

两个刻意的决定：

- **刻意不写 `@ColumnInfo(defaultValue = ...)`**：Room 的 schema 校验只在"实体声明了
  默认值"时才去比对数据库里的默认值，声明了反而更严、更容易踩坑（而 `ALTER TABLE`
  那句 `DEFAULT ''` 是老行必须有值才要的）。
- **尽量回填**：能从来源会话推出人设的就归给那张卡。推不出来的（手工加的、
  来源会话已删的）留成通用 —— **宁可多看一条，也不要让用户发现记忆凭空少了。**

`Migrations.kt` 里同时写清了**这个项目验不了迁移**的原因（`MigrationTestHelper` 走
instrumentation，而项目刻意不引 Robolectric、没有 androidTest），所以只能靠
"导出 schema + 手写 SQL + 拿**真实数据**跑一遍"来验。

## 2026-10-07 · 面对面的节奏、右上角三阶段指示、"一次发多条"暴露的一个防抖 bug

这三件是一起出现的：用户提"面对面时间判断不对"和"批次发送时加个动画"，
测的时候又发现了那个防抖 bug。

### ① 面对面走**另一套节奏**（原来和聊天共用一套公式）

原来的 `Pacing.pace` 不分模式，于是面对面里每条都按聊天那套排：

| 排进去的 | 来源 | 面对面里的值（真机受害场景） |
|---|---|---|
| 打字时长 | `字数 × 110ms`，上限 12s | 一句 20 字旁白 → 2.2 秒"正在输入" |
| 条间间隔 | 模型没给 `gap_ms` 时按 `每个字随机 700~1100ms 累加`，上限 20s | 一句 20 字 → **14~22 秒** |
| 阅读延迟 | 按用户消息长度分档 600~3300ms | 同一个空间里**没有"读消息"这个动作** |

而场景协议明确写着"面对面**不用** `gap_ms`" —— **提示词叫模型别管节奏，
引擎却照着"打字"给每条补了满额节奏**，读起来一顿一顿。

现在 `Pacing.scenePace` 是另一套（`PacingConfig` 里新增 `scene*` 一组参数）：

| 事件 | 间隔 | 打字时长 |
|---|---|---|
| `act` / `scene` | **固定 700ms**，忽略字数 | **0** |
| `say` | `500ms + 字数 × 60ms`，上限 3s（比聊天短得多） | **0** |
| 任何事件，模型显式给了 `gap_ms` | 尊重它 | — |
| 任何事件，模型显式给了 `typing_ms` | — | 尊重它（那是它主动要的"欲言又止"） |

阅读延迟在面对面里退化成固定 **350ms** 的反射时间（`Pacing.sceneReadDelay`）。

接线在 `Player.plan`：把 `event.kind` 在 `event.mode == SCENE` 时作为 `sceneKind` 递下去。
**这条接线是这次最容易静默坏掉的地方** —— 忘了传，面对面就悄悄退回聊天节奏，
没有任何报错，只是"读起来一顿一顿"。所以 `PlayerTest` 里专门钉了一条"接线通没通"。

### ② 右上角指示器：从 1 个状态变成 **3 个**

原来只有"有点动/没在动"两种（一个转圈），而 `pendingHint` 是拿文案当状态用
（`pendingHint.contains("想")` —— 改一个字就崩）。现在 `ChatUiState.turnPhase`
是个类型，三个阶段各有**一眼能分开**的动画：

| 阶段 | 什么时候 | 动画 | 读作 |
|---|---|---|---|
| `BATCHING` | 你按了发送、话还攒着（防抖窗口内） | 三个点**依次点亮** | "你的话还在我手里" |
| `THINKING` | 已经交给模型、等它回 | 转圈 | "在想" |
| `SENDING` | 模型回了，**正在一条一条发出来** | 三个点**上下起伏**（相位错开） | "正在往外说" |
| `IDLE` | 都没在跑 | 无 | — |

`SENDING` 这一段以前**完全没有任何指示**：气泡之间可能隔好几秒（面对面尤其），
屏幕上什么都不动，看起来像"发完了"或者"卡住了"。用竖直方向的运动是为了和
`BATCHING` 的横向"依次点亮"一眼分开。

收尾处抽了个 `endPlaybackPhase()`，它**只在自己确实是 `SENDING` 时才改**——
用户插话时 `send()` 已经把阶段改成 `BATCHING`，而演出协程随之作废也会走到收尾，
无条件写 `IDLE` 会把"你的话攒着"抹掉（两条协程先后不确定，两头都得自洽）。

### ③ 【真 bug】一批里有 ≥2 条、末条又没句末标点 → **那批永远不会被认领**

`scheduleDebounce` 在等完之后会"再看一眼"，而它当年的判据是 `recheck.waitMs > 0`：
"重新判定之后还要等，说明还有新消息在路上，让给下一轮"。

问题是：对"≥2 条、末条无标点"的批次，重新判定**仍然**是 `CHUNKING` 档、
**仍然** `waitMs > 0` —— 于是它每次都让给"下一轮"，而**下一轮根本不存在**
（没有新的 `send()` 就不会再起一个防抖任务）。结果：

- 这一批永远不被认领 → 模型永远不被调用 → 用户看到"我把话发出去了，它一直不回"。
- 只有 1 条消息时不会触发（`gapToPreviousMs == null` → 重新判定是 `NEW_TURN`、`waitMs = 0`），
  所以它躲过了所有既有测试。

**它是被"一次发多条"逼出来的**：用户在三格里分别写了话/动作/环境一起发，
恰好就是一个 ≥2 条的批次。修法是把判据换成**批次本身变没变**：

```kotlin
val batchMark = pending.lastOrNull()?.at
if (decision.tier != DebounceTier.NEW_TURN) delay(decision.waitMs)
if (pending.lastOrNull()?.at != batchMark) return@launch   // 真来了新消息才让路
flushTurn()
```

顺带发现：老的 `连发三条只认领一次 - 每条只有一份` **隐式依赖了这个 bug**
（它自己调 `claimPending()` 去拿批，前提是防抖永远不会开工）。那个 bug 修掉后
它立刻红了 —— 判据已改成从**落盘结果**与**调用次数**看，那才是它真正要守的现象。

### ④ 输入区：三格草稿 + 一起发

面对面里"说 / 做 / 景"是**三条并行**的输入线（你完全可能先说一句、再做两个动作、
再描一下环境，然后一起发），所以：

- 切来切去**各自的内容都留着**（不是清空重来）；当前格用主题色，**另外两格里
  有草稿的比空的亮** —— 不然你写了一半切走，就再也看不出还有东西没发。
- 发送键的可点性看 **三格里有没有非空的**，不是看当前这一格（在"做"里写了一半
  切到空的"景"，发送键不该变灰）。
- 按发送 = **同一批连发 N 条**，每条各自带类型。刻意**不**拼成"一条含多段"的消息：
  那要求 `message.text` 能表达多段各带类型的片段，等于把解析往嵌套方向推
  （见 `UserUtterance` 的注释 —— 那正是该迁到"加一列"的信号）。
  模型侧看到的也就是三行各带标记的话，和它自己一轮分条同形。
- **发消息模式（隔空聊天）不显示这三个开关**，一切按"说"处理；做/景的草稿不清掉，
  切回面对面还在。（代价：那种情况下它们不会发出去 —— 看得见才发得出去。）

### 取证

- 全量测试 **229 个全绿**（core 169 + app 60），0 警告。新增 8 条：
  `PacingTest` 6 条（动作/旁白忽略字数、台词更短、不算打字、留白仍生效、
  `gap_ms` 优先、阅读延迟不按字数）、`PlayerTest` 2 条（面对面不排打字且间隔相同、
  聊天模式不受影响）、`SessionControllerTest.连发两条且末条没标点 - 也必须开工`。
- 真机（用户手动验证）：三态草稿与组合发送**可用**（用户原话"这个是可以的"）；
  右上角两个状态用户已看到并确认"功能是对的"。
- 顺带记一条**踩过的坑**：`uiautomator dump` 里那几个小开关节点的 `bounds`
  报的是**字形位置**，而可点区域是它的盒子（宽度约 22dp）—— 按报出来的中心点
  会落到两个开关的空隙上（表现为"点了没反应"）。用 adb 点这种小控件时，
  坐标要按盒子中心算，或者干脆让**人来点**（这一步后来改成让用户操作了）。

### 已知的小瑕疵（没改）

- 我的动作/环境那两行**没有时间戳**（和对方的动作/旁白一致，但和我自己的气泡不一致）。

## 2026-10-07 · 面对面模式三件事：用户能写动作/环境、助手历史逐条落盘、中断语义纠正

三件事一起做的，因为都落在同一段代码上（播出与历史写入）。

### ① 用户侧也能"说 / 做 / 景"了

**问题**：面对面里用户只能"说话"。他写"把伞收起来"，模型拿到的是一行
`对方：把伞收起来` —— 只能猜那是台词还是动作。而助手侧本来就有标记
（`eventsToAssistantText` 把 `act` 渲染成 `*…*`、`scene` 渲染成 `（…）`）。

**做法**：新增 [`UserUtterance`](../core/src/main/kotlin/app/solochat/core/model/UserUtterance.kt)，
编码成**和助手侧同一套标记**存进 `message.text`：

| 用户选 | 存进 `Message.text` | 界面上画成 | `/api/history` 的 `who` |
|---|---|---|---|
| 说（默认） | `把伞收起来` | 右侧实色气泡 | `me` |
| 做（含感官） | `*把伞收起来*` | 右侧斜体暗色小字 | `my_action` |
| 景（环境） | `（楼道灯闪了一下）` | 居中灰字（与对方写的旁白同一种） | `scene` |

**为什么不加一列 `message.kind`**：那要写这个仓库的**第一条 Migration**。
`SoloChatDatabase` 是 v1、没有任何迁移、且刻意没用 `fallbackToDestructiveMigration`
（"宁可启动失败也不静默清库"），而线上是真实数据 —— 写错了就是"升级后打不开 App"。
而"标记进文本"**助手侧早就是这么干的**，等于沿用既有约定，零迁移。
编解码集中在一个纯函数里、由 11 条测试钉住（重点是**误判**：`我明天*可能*来`
里的星号不该被当成动作）。等真要加第四五种类型、或规则需要转义时再迁到"加列"。

**界面**：输入框胶囊内部左侧多了一个 `说 / 做 / 景` 开关（点一下循环，默认"说"，
所以常用路径零操作），占位文字随类型变（`你在做什么…` / `周围发生了什么…`）。
投影层新增 `ChatItem.MyAction`；我的环境描写**不单开一类**，直接复用 `Narration`
（环境是无人称的，谁描述都一样）。

**协议段**：`10-protocol-scene.txt` / `10-protocol-chat.txt` 各加了一节，告诉模型
"对方发来的东西也是带标记的、怎么读"。不写这一节，模型会把 `对方：*把伞收起来*`
当成一句带星号的台词。

### ② 助手历史：整场演完写一次 → **播完一条就写一条**

**问题**（用户指出，核实后确实成立，而且是三个窗口）：

1. **竞态**：用户插话时 `send()` 先 `interruptPlayback()`（它 `scope.launch` 去写历史），
   紧接着 `scheduleDebounce()` 若判成"新话题"档（`waitMs = 0`）会**立刻**
   `flushTurn → startTurn → buildPrompt` 读消息表。两条协程在同一个 IO 调度器上，
   顺序不保证 —— **下一轮可能读不到上一轮刚出口的话**。
2. **进程被杀**：已经出口的气泡在事件表里是 `DELIVERED`（界面上也画得出来），
   但消息表里没有 → 模型永远看不到自己说过什么。这正是 docs 记过的
   "界面看起来对、模型看不到"那类故障。
3. **时间戳**：整轮共用一个写入时刻，而每条气泡其实是各自在某一刻出口的。

**做法**：`persistSpokenAssistantMessage(整轮)` → `appendSpokenAssistantLine(单条)`，
在 `runPlayback` 每条落定的那一刻写；`interruptPlayback` 的两个分支也顺手补写
（防"已落定、还没写"那一瞬间），用 `Playing.writtenIds`（`synchronizedSet`）防重。

**连带的必要修改**：`dropRepeatedFromPreviousTurn` 原来只看"上一条 assistant 消息"的
整段文本 —— 一条一消息之后那变成"只跟最后一句比"，判据会松掉一大截。现在按
`turnId` 把**上一轮的全部** assistant 消息合起来比。

### ③ 中断语义：`INTERRUPTED` 不等于"说了一半"

**发现**（核实用户提问时查出来的）：正在播的那条被打断后会被标成 `INTERRUPTED`，
而**界面最终会把它的完整正文画出来** —— 投影的门禁是 `delivery.spoken`，
`INTERRUPTED` 也算出口。也就是说**用户看到的是整句，没有"半句话"这回事**。

真正错的是提示词：`interruptedNote` 写的是"你上一条还没说完"，而模型据此会以为自己
表达得支离破碎、于是重新组织一遍已经说过的话。**事实是：那句话说出去了，
是后面本来要接着说的那些没出口。**

**做法**：只改文案，**不改行为**（行为本来就是对的 —— 当前这条补完、后面的取消）。
`DeliveryState.INTERRUPTED` 的 KDoc 也一并写清楚了这个反直觉的事实，
免得下一个人又照字面去推断。

> 这条值得记：我一开始的提议是"把当前这条标成已说完"，听起来是在修一个观感问题 ——
> 但**那个观感问题并不存在**（界面一直画的是完整正文）。如果照着改，就是又一次
> "为了界面上想象出来的问题去动领域语义"，正是 docs 里已经记过的那类错。
> **先量，再改。**

### 取证

- 全量测试 **220 个全绿**（core 161 + app 59），0 警告。新增：
  `UserUtteranceTest`（11 条）、`ChatProjectorTest` 3 条（用户动作/环境/普通气泡）、
  `SessionControllerTest.插话打断不会丢掉已出口的那条`；并把
  `下一轮能看到我上一轮说过的话` 的断言从"一轮一条 assistant 消息"改成
  "一个气泡一条、两句都在"（新形状）。
- **真机**（`PKM110`，在**新建的**对话里跑的）：输入框左侧开关点一下从 `说` → `做` → `景`；
  发一条动作、一条环境，界面上分别是**右侧斜体**和**居中灰字**，星号与括号都被剥掉；
  `/api/messages` 里存的是 `*ba san shou si qi li*` / `（lou dao deng shan le）`，
  且助手历史确实是**两条独立消息**；`/api/history` 的 `who` 是 `my_action` / `scene`。
  模型也按新约定读懂了（把动作当动作、把环境当环境接）。

### 已知的小瑕疵（没改）

- 我的动作/环境那两行**没有时间戳**（和对方的动作/旁白一致，但和我自己的气泡不一致）。
  要补的话得给 `ChatItem.MyAction` 加 `at` 字段，是独立的一小步。

## 2026-10-07 · 模式切换不再伪造一条"我"的消息

### 原来的样子

点"好，进去"之后，聊天里会冒出一条**蓝色气泡**（"我"发的），写着
`[系统] 你们见面了，开始面对面。`。

两个身份同时错了：

| 视角 | 看到的 |
|---|---|
| 用户 | 一条**我自己发的**系统通知 |
| 模型 | `对方：[系统] 你们见面了，开始面对面。` —— 它会以为对方说了这么一句 |

根因在 [SessionController.applyMode](../app/src/main/kotlin/app/solochat/play/SessionController.kt)：
它写了**两次**——一条 `MessageRole.SYSTEM`（"—— 见面了 ——"，对），
外加往待处理队列里塞一条 `IncomingMessage("[系统] …")`（错）。后者存在的唯一目的
其实是"触发下一轮"，但待处理消息一律以 `MessageRole.USER` 落库、以
`ChatItem.Mine` 显示（见 `persist()` / `pendingAsItems()`）。

### 改法：把"这时候该干嘛"从消息里挪进提示词

| 层 | 改动 |
|---|---|
| `AgentTurn` | 新增 `cue: String = ""` —— 引擎插的"台上提示"，**不落成任何一方的消息** |
| `PromptContext` | 新增 `cue`，与 `interruptedNote` 同类（引擎事实，只进变动区） |
| `PromptBuilder` | 变动区末尾新增 `### 刚刚` 段（放最末尾：离历史最近，指令最不容易被忽略） |
| `AgentTurnRunner` | 把 `turn.cue` 传下去，并在 `阶段: 请求` 日志里加一行 `台上提示` —— 空批次 + 有提示 = "是引擎叫她开口"，否则会被误读成"模型自己抢话" |
| `SessionController` | `flushTurn` 里抽出 `startTurn(conversationId, batch, cue)`；`applyMode` 不再碰 `pending`，改成 `startTurn(id, emptyList(), cue = …)` |

切换这件事现在只有**一个**痕迹进历史：那条 `MessageRole.SYSTEM` 消息
（界面上就是"—— 见面了 ——"这行小字）。而 `### 刚刚` 那一句让模型知道"现在开个场"。

### 取证

- 回归测试（两条，都钉住具体现象）：
  - `SessionControllerTest.模式切换只留一条系统小字 - 不产生我发的话`
    —— 断言用户消息数 = 0、SYSTEM 消息恰好一条、那一轮仍然调用了模型
  - `PromptBuilderTest.台上提示进变动区 - 不伪装成谁说的话`
    —— 断言 cue 在系统提示里、排在 `### 当前模式` 之后、且历史里一个字都没有
- 全量测试：core **150** + app **55** = **205** 全绿，0 警告
- **真机**（`PKM110`，在一个**新建的**对话里，没有污染既有会话）：
  发 `wo dao ni lou xia le` → 确认卡片 → 点"好，进去" → 标题栏变 `面对面`；
  界面上**没有**蓝气泡；`/api/messages` 的消息表：

  ```
  [user     ] wo dao ni lou xia le
  [assistant] 来了 / 等我两分钟，换双鞋
  [system   ] —— 见面了 ——
  [assistant] （楼道口的声控灯亮了一下又灭，夜里的风带着点凉）
              *小默从单元门里出来，外套还没穿利索，一只手在袖子里找口子*
              你怎么站那儿不动
  ```

  `含 [系统] 的用户消息条数 = 0`。最后那条 assistant 消息同时证实了提示词的
  `### 刚刚` 生效了 —— 模型自己开了场，而不是等对方先说话。

## 2026-10-07 · 输入栏：压掉 material3 的 56dp 内置高度，并让开屏幕圆角

### 一、高度：`TextField` 有一个压不下去的下限

[ChatScreen.ChatComposer](../app/src/main/kotlin/app/solochat/ui/chat/ChatScreen.kt) 原来写的是
`Modifier.heightIn(min = 44.dp, max = 132.dp)`，但真机实测（560dpi）：

| | 数值 |
|---|---|
| 当时的输入框 | 196px = **56dp** |
| 代码里写的下限 | 44dp —— **完全没生效** |

原因是 material3 的 `TextField` 自带上下各 16dp 的内边距，加一行字（24dp）就是 56dp；
`heightIn(min = 44.dp)` 设的是**约束下限**，压不动内容自身的尺寸。

改成 `BasicTextField` + 自己画的圆角底（高度、内边距、占位符全自己定）：

| | 改前 | 改后 |
|---|---|---|
| 输入框高 | 56dp | **40dp** |
| 垂直内边距 | 内置 16dp × 2 | 自定 8dp × 2 |
| 整条输入栏 | 62dp | **50dp** |

多行仍然跟着长（`heightIn(max = 132.dp)`，`maxLines = 5`）。

### 二、左下角被屏幕圆角切掉：`dumpsys display` 给了准确数字

用户报的是"输入栏左下角不在可见范围内"。`dumpsys display` 里的
`roundedCorners` 给出了答案：

```
RoundedCorner{position=BottomLeft, radius=140, center=Point(140, 2620)}
```

屏 1256×2760、四角半径 **140px（40dp）**。输入栏自己的圆角是 20dp（70px），
它的左下角圆弧中心因此落在 `(start+70, 2760-bottom-70)`；整段圆弧可见的条件是它
落在屏幕圆角**之内**：

```
(start + 70 - 140)² + (2760 - bottom - 70 - 2620)² ≤ (140 - 70)²
```

| | start / bottom | 左边那个和 | 判定 |
|---|---|---|---|
| 改前 | 8dp(28px) / 4dp(14px) | 42² + 56² = **4900** | 正好等于 70² —— 卡在边界上，所以被切 |
| 改后 | 16dp(56px) / 6dp(21px) | 14² + 49² = **2597** | 圆弧中心离屏幕圆心 51px，余量 **19px ≈ 5.4dp** |

底部只加了 2dp（余量从 13px 提到 19px），整条输入栏仍然比改前矮 12dp。

> ⚠️ **这件事截图看不出来**：`screencap` 拍的是整个矩形帧缓冲，圆角是物理显示区域的
> 属性。所以判据只能是"用 `dumpsys` 拿到半径 + 算"或者"人眼看"。别拿截图当证据。

### 取证

- 像素扫描量到的输入栏底色块：`x 56..1017`、`高 140px = 40dp`、`距屏底 21px = 6dp`
  （`uiautomator` 报的 `EditText` 边界是 **168px**，比真实底色块大 —— 那是语义节点的
  膨胀，量几何不要用它）
- 把屏幕圆角的圆弧画在截图上叠加看过：输入栏左边缘与圆弧之间有肉眼可见的间隙
- 真机装机跑过；`assembleDebug` 0 警告

## 2026-10-07 · 进行中提示：输入框上方的横幅 → 标题栏一个转圈

### 原来的样子

`ChatScreen` 里有一个 `HintRow`，横在**输入框正上方**，画的是 `ChatUiState.pendingHint`

### 为什么改：那个字段每一轮至少被写两次

`pendingHint` 的写入点（[SessionController.kt](../app/src/main/kotlin/app/solochat/play/SessionController.kt)）：

| 时机 | 写进去的内容 | 位置 |
|---|---|---|
| 防抖判定完 | 判定理由：`一句完整的话，直接回` / `你在分开发的，再等一下` / `新的话题，直接回` … | `:334` |
| 请求已经发出 | `正在想…` | `:553` |
| 模型说 `wait`（这一轮不回复） | `AgentEvent.Waiting.reason` | `:556` |
| 脚本就绪 / 静默 / 失败 | `""`（清空） | `:348` `:559` `:571` `:577` |
| 用户插话打断 | 打断原因 | `:923` |

于是**每发一条消息**，输入框上方都要闪一遍"判定理由 → 正在想…"。

而判定档位本来是**给排查看的**：`Debounce` 的注释写了档位是"给人看的解释，不是给机器算的分支"
（[Debounce.kt](../core/src/main/kotlin/app/solochat/core/protocol/Debounce.kt)），
`02-handoff.md` 也把它列为排查手段。**"给人看"指的是排查时能从日志里读到，
不是每一轮都糊在聊天区、还把消息流顶来顶去。**

### 改法

只动一个文件：[ChatScreen.kt](../app/src/main/kotlin/app/solochat/ui/chat/ChatScreen.kt)

| 位置 | 改动 |
|---|---|
| `TopAppBar(actions = { … })` | **新增**：`pendingHint` 非空时画一个 `CircularProgressIndicator`（18dp，`strokeWidth = 2dp`） |
| 消息流与输入区之间 | **删掉** `if (state.pendingHint.isNotBlank()) HintRow(...)` |
| 文件内 | **删掉** `HintRow` composable（删掉调用点后它就成了死代码） |
| import | `androidx.compose.foundation.layout.widthIn` → `androidx.compose.foundation.layout.size` |
| 文件头 KDoc | 补一句"输入区上方不再有任何提示行"，免得下一个人以为漏了什么 |

**开关为什么取 `pendingHint.isNotBlank()`，而不是只认 `"正在想…"`**：
这个字段覆盖的是整段"**这一轮在动**" —— 防抖等待（最长 30 秒，`Debounce.HARD_CAP_MS`）
加上模型调用。只认 `"正在想…"` 会让那最长 30 秒的等待**一点反馈都没有**，
而用户在那段时间里最容易以为软件卡死了。

### 刻意**没有**改的（和改了什么一样重要）

- **`ChatUiState.pendingHint` 字段与上表全部 8 处赋值原样保留。**
  日志里的 `阶段: 防抖判定`、以及"点标题栏打屏幕快照"（`dumpScreenState`，
  [02-handoff.md](02-handoff.md) §5）都还在读它。这次改的是**画不画**，不是**记不记**。
- **`SessionController` / `Player` / `ChatProjector` / `core` 零改动。**
  所以 [02-handoff.md](02-handoff.md) §3 那六条不变式一条都没被碰到，
  203 条测试钉住的语义也没动。
- `SessionControllerTest.awaitSettled` 拿 `pendingHint.isEmpty()` 当"这一轮跑完了"的
  收敛条件 —— 字段还在写，所以它照旧成立（这也是不能顺手把字段删掉的原因之一）。

### 取证

| 手段 | 结果 |
|---|---|
| 编译 | `pwsh tools/build.ps1 :app:assembleDebug` → BUILD SUCCESSFUL，**0 条 `w:` 警告**，APK 14.6 MB |
| 单元测试 | `:core:test` **149** + `:app:testDebugUnitTest` **54** = **203 全绿**（0 失败 / 0 错误 / 0 跳过） |
| 真机 | `PKM110`（adb `3B6F65E5PBRYSBDL`）。流程：`adb install -r` → 进「呆猫」会话 → 点输入框 → `input text zaiganma` → **重新 dump 查发送键坐标** → 点发送 → 连拍（两轮，12 帧 / 10 帧） |

真机结果的判据，两条：

1. **标题栏右上角出现转圈** —— 两轮连拍都在**第 2 帧**抓到（第 1 帧还在发送前的状态）。
   转圈消失的那一帧，标题栏第二行同时从上一轮的 `4112 tokens · ¥0.0007`
   变成这一轮的 `4199 tokens · ¥0.0009`，说明转圈与"这一轮在跑"是对齐的。
2. **输入框上方从头到尾只有消息气泡**，没有任何提示行 —— 原横幅的位置被单独裁出来逐帧看过。

> 取证时用的是 ASCII（`zaiganma`）：`adb shell input text` 不支持中文，
> 见 [02-handoff.md](02-handoff.md) §4 第 8 条。所以模型回了一句"你怎么打拼音了" —— 那不是 bug。

### 已知限制 / 没验的部分

- **防抖的理由文字现在哪里都不显示。** 转圈只回答"它在动"，不回答"它为什么还不回"。
  如果之后觉得需要，把它接到标题栏第二行（跟在 `呆猫 · 发消息` 后面）即可 ——
  字段还在，界面接一下就行。
- **长时间防抖下的转圈没有真机取证。** 上面那一轮正好命中"距上一条超过 60 秒 = 新话题直接回"，
  防抖被跳过，抓到的窗口只覆盖模型调用那 1~2 秒。代码上 `pendingHint` 在整个防抖窗口内非空，
  所以转圈会持续 —— 但"代码上会"不等于"真机上看到了"。
  想补这一条：连着快速发四条短消息，然后连拍。
- 转圈在 `TopAppBar` 的 `actions` 里，是标题栏**唯一**的 action，不存在点击区重叠
  （那个坑见 [02-handoff.md](02-handoff.md) §4 第 6 条）。

### 怎么回退

这个仓库**没有 git**（无 `.git`），所以回退得手工做：把 `HintRow` composable 和
`if (state.pendingHint.isNotBlank()) HintRow(...)` 那个调用点加回消息流与输入区之间，
再删掉 `TopAppBar` 里的 `actions` 块。`pendingHint` 一直在写，界面写回去就能还原到旧行为。

### D. 本机环境：工作区写权限只落在根目录（换会话可能重现）

某次会话启动时，沙箱在工作区**根目录**授予的写权限**没有传播到任何已存在的子目录**，
而新建的子目录反而是可写的。症状：

- `core/` 里连一个源文件都改不了；
- Gradle 连 `.gradle-home/wrapper/dists/…/gradle-8.9-bin.zip.lck` 都建不了，报
  `FileNotFoundException … (拒绝访问)`；
- 但工作区**根目录**下新建目录、往里写文件都正常 —— 这个不对称就是判据。

绕过办法：把该会话切到**完全权限**（命令与文件编辑随即正常）。
根治办法不明：用 `diagnose-windows-sandbox-acl` 在根目录上重跑一次，
返回 `NOT_THIS_CLASS`（根目录权限已齐、无需再改），所以**没能**把权限推给子目录。
